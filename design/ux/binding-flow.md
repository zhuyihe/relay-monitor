## 一句话说清

**你只需要知道三样东西：**

- **你的站**（自营站点）：里面有很多渠道。
- **上游**：一个上游网站上的一个账号。下面有好几把 Key，每把 Key 在上游的一个分组里；分组不同，价钱的倍率不同（倍率 1.2 就是按标价的 1.2 倍收钱）。
- **渠道和 Key**：你站里的每个渠道都填着上游的一把 Key。一个上游对应你站里好几个渠道；换了 Key，渠道还是那个渠道。

**利润 = 渠道每天的收入 − 这个渠道当天用的 Key 在上游花的钱。**

- 渠道的收入：你站里的用户当天在这个渠道上消费的钱，读你站的用量记录。
- 上游花的钱：读上游的账单（每条用量记录上游已经按当时的分组、倍率算好了钱），不是控制台自己按倍率估。
- 两边都换成人民币再相减，和现在一样：你站用「售价」（设置自营站点抽屉的「更多设置」里，1 美元额度卖多少元），每个上游用它的「汇率」（加上游抽屉的「更多设置」里）。都可以不填：没填时数照样出来，暂按 1 美元 = 1 元算，数前带「≈」，利润等式下面写一句原因，那一处有「去设置」。所以不在下面的 9 下里。

**系统怎么知道每个渠道用的是哪把 Key**：你站的服务器上，和 New API 放在一起跑一个**只读的小服务**（叫「渠道 Key 读取服务」，下面简称读取服务）。它读你站每个渠道里填的 Key，只交出打码的样子（前 4 位、后 4 位）和一个比对用的指纹，不交出完整的 Key。控制台拿它和每个上游的 Key 一把一把对，对上了就是那个上游的那把 Key，不猜。换了 Key，1 分钟内跟上。你站搬服务器时，它跟着一起搬，控制台不用改。

每一天的利润只会是三种状态之一（ui-copy-spec §4）：

- **实时**：今天，数还会变；或者过去几天的数系统还在读（最多 7 天），写「还在读取」。
- **已固定**：过去的日子，都读全了，数定下来了。
- **需处理**：不处理就算不准，利润写「—」。

汇总只加算出来的：需处理的、还在读取的都不加，汇总旁边写一句没算进来什么，例如「其中 1 个渠道需处理、2 个还在读取，没算进来」（ui-copy-spec §4）。

**你只做三步：**

1. **设置自营站点**：填地址、超级管理员的访问令牌、读取服务的令牌，只做一次。读取服务要在你站的服务器上装好（docker compose 里加几行，开发给）：先打开这个抽屉，把「怎么装」里的几行交给管服务器的人，装好后再填令牌；读取服务令牌可以先空着保存。
2. **加上游**：填地址和令牌，回答一次「这个上游账号只给你自己的渠道用吗？」。
3. **开始算利润**：系统列出用这个上游的 Key 的渠道，你点「开始算利润」。

以后换 Key 不用管，系统自己跟上。上游账号只给你自己的渠道用时，只有三种情况会找你，每次只给一个按钮：

- 渠道换成了一把不在已加上游里的 Key（「加上游」）；
- 上游或你站的登录过期了（「更新登录信息」）；
- 读不到你站的渠道 Key（「检查连接」）。

账号别处也在用、或者你答了「不确定」，多两种：「去回答」，和新连上来的渠道还没算利润（「开始算利润」，附录 2）。很少见的还有四种：一把 Key 在两个在算的渠道之间挪过（「改时间」，第 3 节）；上游的令牌少了读完整 Key 的权限（「更新登录信息」，附录 8）；账单超过 7 天还没读到的日子（「重新读取」，例外二）；自营站点不记收费记录了（「重新检查」，附录 9）。

下面说的「三步」是三件事；每件事里要填、要点的加起来一共 9 下（第 6 节）。

第 7 节和写着「§N」的地方是给开发、写规范的人看的，只看流程可以跳过。

## 1. 主流程：从零到看到利润

每一步三栏：你看到什么、你点什么、系统在后面做了什么。系统做的事你看不到，也不用点。

### 第 0 步（在你站的服务器上，只做一次）：装读取服务

不在控制台里做，由管你站服务器的人做：

- 在你站的 docker compose 里加几行（具体几行开发给，放在设置自营站点抽屉的「怎么装」里，可以直接复制），设一个读取服务的令牌，重启。它默认用 New API 同一套数据库设置，不用另填；想更稳妥的，另建一个只能查渠道表的数据库账号给它（「怎么装」里写怎么建）。
- 有反向代理的，把一个固定路径转给它（默认地址就是「站点地址 + 这个路径」）；没有反向代理、直接开端口的，在抽屉的「更多设置」里填那个端口地址。「怎么装」里两种都写。
- 它用 New API 自己的数据库设置去读渠道，只读，不改你站的任何东西；数据库不用对外开放。
- 不管哪种，都要走 HTTPS（「怎么装」里写怎么配）。

### 第 1 步：设置自营站点（样稿 flow-own）

| 你看到什么 | 你点什么 | 系统在后面做了什么 |
|---|---|---|
| 一个抽屉，三栏：「站点地址」「超级管理员的访问令牌」「读取服务令牌」。访问令牌下面一句写去哪里拿（在你站的后台用超级管理员登录，「个人设置」里生成）；读取服务令牌下面一句「装读取服务时设的那个令牌，至少 32 个字符；「怎么装」里有生成它的命令」，旁边一个收起区「怎么装」 | 填这三栏 | —— |
| 填完、离开输入框，下面各一句：「能读到：站点「我的站」，120 个用户，6 个渠道」「能读到：6 个渠道的 Key」 | —— | 读你的站：站点名、用户、每个渠道；读读取服务：每个渠道里填的 Key（只拿打码和指纹） |
| 「更多设置」（默认收起）里是售价（1 美元额度卖多少元），和读取服务的地址（默认是「站点地址 + 固定路径」，装在别处时才改）；都不填也能保存 | —— | —— |
| 底部「保存」 | 「保存」 | 记下来。以后每天读每个渠道的收入，每分钟读一次每个渠道的 Key |

- 站点读不到时，那一句换成原因（ui-copy-spec §8.2），「保存」灰着。
- 读到自营站点不记收费记录时，照附录 5 的样子：「保存」照样能点，但第 3 步不能开始算利润，那一句下面写「自营站点不记收费记录了，渠道的收入读不到；在自营站点后台打开：系统设置 → 运维 → 日志维护 →「记录配额使用量」（旧版界面是：运营设置 → 日志设置 →「启用额度消费日志记录」），才能开始算利润」（附录 9）。
- 令牌读不到自营站点的设置时（不是超级管理员，或者新式令牌少了「读设置」的权限），那一句下面多一行原因（ui-copy-spec §5.4），不挡保存，也不挡开始算利润（附录 10）。用普通管理员的令牌也能连上，只是读不到设置。
- 读取服务令牌不到 32 个字符时，那一句写「令牌至少 32 个字符，用「怎么装」里的命令生成一串」，「保存」灰着。
- 读取服务令牌空着、或者读不到时，那一句写「还没装读取服务」或原因（例如「读不到渠道 Key：连不上 https://my.example.com/…」）；「保存」照样能点，自营业务的收入照常算，但第 3 步不能开始算利润：渠道照样列出，顶上一句「装好读取服务才能开始算利润」，旁边是同一个「怎么装」；不让人自己选 Key，也没有「指定 Key」（用户 10-25 定：不用兜底）。

### 第 2 步：加上游（样稿 flow-upstream）

| 你看到什么 | 你点什么 | 系统在后面做了什么 |
|---|---|---|
| 一个抽屉，两栏：「站点地址」「令牌」；令牌下面一句写去上游后台哪里拿（ui-copy-spec §3.7 那几句，按认出的类型换） | 填这两栏 | 填地址时认出是哪种上游（New API 或 Sub2API），令牌那一栏的名字和说明跟着变（「访问令牌」或「登录令牌」）；先按令牌读账号；读不了，再当成一把 Key 试，读得到就是只填了一把 Key 的上游（附录 1） |
| 填完、离开输入框，下面一句「能读到：账号 演示·主力账号，余额 $158.78，3 把 Key」 | —— | 读这个账号：账号名、余额、Key 列表（每把 Key 的名字、分组、倍率）；试读一次账单，确认每天的账单能读全；定好按哪个时区算一天 |
| 一个问题「这个上游账号只给你自己的渠道用吗？」，三个选项一个都不预先选 | 选一个 | 记在这个上游上 |
| 底部「加上游」 | 「加上游」 | 记下来。接着拿这个上游的 Key 和你站每个渠道的 Key 对（第 3 步） |

- 选「只给我的渠道用」：以后换 Key 系统自己跟上，新渠道系统自己开始算。
- 选「别处也在用」或「不确定」：见附录 2。
- 还没设置自营站点时，加完就停在这里，提示「已加上游」。以后设好自营站点、点「保存」时，设置自营站点的那个抽屉接着出第 3 步，已加的上游一个一组列出来。

### 第 3 步：开始算利润（样稿 flow-start）

加完上游，同一个抽屉直接换成这一步，不关、不跳页。

| 你看到什么 | 你点什么 | 系统在后面做了什么 |
|---|---|---|
| 标题「开始算利润」，下面列出你站里用这个上游的 Key 的渠道，一个渠道一行：渠道名「高速 A」，下面一句「用的 Key：oai · 分组 a · 倍率 1.2」（Sub2API 上游读不到倍率，只写到分组：「用的 Key：oai · 分组 a」），默认都勾上 | 想不算的可以取消勾 | 拿读取服务读到的每个渠道的 Key，和这个上游的 Key 一把一把对，对上的就列出来 |
| 底部「开始算利润（4 个渠道）」 | 「开始算利润」 | 从点的这一刻起，每天按「渠道收入 − 这个渠道当天用的 Key 在上游花的钱」算；点之前的日子不补算（和现在一样，今天写「从 14:30 开始统计」） |
| 抽屉关上，落到「每日利润」的今天，这 4 个渠道高亮一下，今天的数已经在（实时） | —— | 之后每天自己算；过了零点、都读全了，那天标「已固定」（ui-copy-spec §4 的规则，不变） |

- 一个渠道都没对上时写「你站里没有渠道用这个上游的 Key」，下面一句「渠道里换成这个上游的 Key 以后，系统会自己找到」。
- 你在这一步取消勾的渠道，以后也不算，除非你在「渠道」页签里点它的「开始算利润」。
- 以后你站里有渠道填上这个上游的 Key（新加的渠道，或者原来用别的 Key、现在换成这个上游的）：系统 1 分钟内找到，自己开始算，「渠道」页签上这个渠道写「10月26日 09:12 起系统自动开始算」，不来找你（用户 10-25 定）。只对答过「只给我的渠道用」的上游这样做；你取消过勾、点过「停止算利润」的渠道不自己开始。
- 两个渠道填了同一把 Key：这把 Key 的上游成本只算一次，两个渠道合起来算利润，在每日利润里并成一行「高速 A、高速 B（同一把 Key）」（和现在一把 Key 对几个渠道一样）。第 3 步里它们也是一行、一个勾：一起算或一起不算，不会把整把 Key 的成本压到其中一个渠道上。
- 「停止算利润」：从点的那一刻起不再算；已经算出来的日子留着，以后可以再点「开始算利润」接着算。

## 2. 只在三种情况找你（上游账号只给你自己的渠道用时）

每次只给一个按钮，点了就在原地做完。

### 例外一：渠道换成了一把不在已加上游里的 Key（样稿 flow-attention）

多半是你在站里给渠道填了一个还没加进控制台的上游的 Key。

| 你看到什么 | 你点什么 | 系统在后面做了什么 |
|---|---|---|
| 需处理里一条「渠道「高速 A」用的 Key 不在已加的上游里」，说明「从 10月25日 15:20 起这个渠道的上游成本算不出；把这把 Key 所在的上游加进来就能算」，按钮「加上游」。每日利润里这个渠道从那时起是「需处理」，利润写「—」，收入和成本都不算进汇总（不会因为少算成本而虚高） | 「加上游」 | —— |
| 第 2 步的抽屉，站点地址已经按这个渠道里填的地址填好 | 填令牌、回答一次、「加上游」 | 新上游的 Key 里对上了这个渠道的 Key |
| 接着是第 3 步，这个渠道勾着；新上游答的是「只给我的渠道用」时，从 15:20 起接着算，那几天重算（它本来就在算，只是中间缺了成本；同一个列表里从没算过的渠道照第 3 步，从现在起算） | 「开始算利润」 | 需处理那条消失 |

- 是只填了一把 Key 的上游换了 Key：不用加上游，在上游列表里改这个上游的 Key（附录 1）；需处理那条的说明也这样写。
- 你本来就不想算这个渠道：在「渠道」页签里点「停止算利润」，那条就消失。
- 没在算利润的渠道（从来没开始算过）用的 Key 不在已加的上游里，不进需处理，列在「渠道」页签最下面一组（附录 4）。

### 例外二：上游或你站的登录过期了

| 你看到什么 | 你点什么 | 系统在后面做了什么 |
|---|---|---|
| 需处理里一条「登录信息不对或过期了」，说明「更新之后才能接着读取余额和账单」，按钮「更新登录信息」 | 「更新登录信息」 | —— |
| 一个小窗，只有「令牌」一栏 | 填新令牌，点「更新登录信息」 | 用新令牌读一次，读到就接着读余额和账单；过期这几天的账单补读回来（读不到的那几天原来是「实时 · 还在读取」，补读后照常定下来，变成已固定；超过 7 天的那几天系统不再自动重读，留在「需处理」，每天一个「重新读取」） |
| 需处理那条消失 | —— | —— |

你站的登录过期也一样，小窗里填的是超级管理员的访问令牌。

### 例外三：读不到你站的渠道 Key（样稿 flow-attention）

读取服务停了、令牌改了、你站搬了服务器还没装好时会这样。连续 10 分钟读不到才进需处理（偶尔一两次没读到不打扰你）；下面说的「15:19」是读不到之前最后一次读到的时刻（15:20 那次没读到）。

| 你看到什么 | 你点什么 | 系统在后面做了什么 |
|---|---|---|
| 需处理里一条「读不到你站的渠道 Key」，说明「从 15:19 起各渠道的利润先不算；连上以后接着算」，按钮「检查连接」 | 「检查连接」 | —— |
| 设置自营站点的抽屉，停在「读取服务令牌」那一栏，下面写读不到的原因（例如「连不上 https://my.example.com/…：超时」）；「怎么装」收起区就在旁边 | 改令牌（或请管服务器的人把服务重新起来），离开输入框，点「保存」 | 读一次；读到了，那一句变成「能读到：6 个渠道的 Key」 |
| 需处理那条消失 | —— | 拿读到的 Key 和读不到之前的比（见下） |

读不到的那段时间里，数怎么显示：

- 从最后一次读到的时刻（15:19）起，系统照那次读到的 Key 接着读上游账单，但这段时间的数不当准数：每日利润里各渠道写「实时 · 还在读取」，不算进汇总；过了零点也不变成已固定。头 10 分钟里也是这样显示，只是还不进需处理。
- 连上以后，每个渠道的 Key 和读不到之前一样：这段时间的数照常算进汇总、照常固定，不提示。
- 有渠道的 Key 和读不到之前不一样：照第 3 节「换 Key 的时刻怎么定」那条规则，a 是最后一次读到的时刻（15:19），b 是重新读到的时刻（16:05）。钱不受影响，不来问你；「用过的 Key」写第一条用量的时刻（例如「15:42 起 oai-2」），定不出时写「15:19–16:05 之间换成 oai-2（读不到渠道 Key 的那段时间里换的）」，然后照常算、照常固定。
- 只有一把 Key 在两个在算的渠道之间挪过时才问你：需处理里一条「Key「oai-2」从「高速 A」挪到了「标准 B」，不知道是几点挪的」，按钮「改时间」，小窗里默认「重新读到的时候（10月25日 16:05）」，可以改成 a 到 b 之间的任何时刻；定了以后那几天重算。平时（不在读不到的那段时间里）互换了 Key 也一样，默认填读到的那一刻。这是「改时间」在这条流程里唯一出现的地方。
- 读不到超过 7 天还没连上：那几天按 ui-copy-spec §4 变成「需处理」，需处理里还是同一条；连上以后，Key 没变的照样定下来。

## 3. 换 Key、换倍率时

**你不用做任何事**（账号只给你自己的渠道用时。新 Key 不在已加的上游里是例外一；账号别处也在用见附录 2；只填了一把 Key 的上游见附录 1，那种上游换 Key 要你自己改）。

| 发生了什么 | 系统做了什么 | 你在哪里看得到 |
|---|---|---|
| 渠道里的 Key 换成了同一个上游的另一把 | 1 分钟内读到新 Key。上一次读到旧 Key 到这一次读到新 Key 之间那一分钟单独成一段，段里两把 Key 的账单都读，所以换 Key 那一分钟里花的钱算进来了（见下） | 「渠道」页签这个渠道下面的「用过的 Key」多一行「10月24日 14:30 起　oai-2 · 分组 a · 倍率 1.2」（Sub2API 只写到分组）；每日利润那天写「今天 14:30 换了 Key」，那天的状态（实时 / 已固定）不因为换 Key 而变；那天的计算明细里上游成本按两把 Key 分开写 |
| 渠道里的 Key 换成了另一个已加上游的 Key | 同上；这个渠道从旧上游下挪到新上游下接着算（新上游答过「只给我的渠道用」时） | 同上；新上游答的是别的，照附录 2 |
| 同一把 Key 换了分组或倍率 | 从变的那一刻起分成两段记（上游账单里的钱已经是按新倍率算的） | 「用过的 Key」多一行；计算明细写「倍率在 14:30 从 1.0 变成 1.2，分两段算」 |

- 不弹提示、不推送、不进需处理。
**换 Key 的时刻怎么定（一条规则，K 方案第五节用同一段话）**：读取服务每分钟读一次。上一次看到旧 Key 的时刻记作 a，这一次看到新 Key 的时刻记作 b，a 到 b 单独成一段，段里两把 Key 的账单相加，就是这个渠道这段时间花的钱，不漏也不重（两把 Key 都只给这个渠道用：旧 Key 换掉以后没有用量，新 Key 换上以前没有用量）。「用过的 Key」里写的时刻：能从新 Key 在上游的第一条用量精确定出的（New API、Sub2API 的逐条用量都记到秒），系统自动定在那一刻，写「14:30 起 oai-2」；定不出的（上游读不到逐条的用量，或者新 Key 在这段里还没有用量），a 到 b 不超过 2 分钟（两次轮询）时写「b 起」，更长时写「a–b 之间换成 oai-2」。只有一把 Key 在两个在算的渠道之间挪过（例如两个渠道互换了 Key）、靠用量分不清这把 Key 的钱该算给哪个渠道时，才进需处理问「改时间」，默认填 b。跨零点也一样，每天只取这一段落在当天的那部分。

- 上百个渠道时，「渠道」页签按上游分开，一次只看一个上游的渠道；左边上游列表有需处理的排在前面。

## 7. 系统怎么做到（给开发核对）

每一个「系统自己做」的步骤，写明靠什么、有什么前提、做不到时怎么办。开发 10-25 都核过：上游那几行（全文 `~/.cache/relay-monitor-copy/binding-flow-check.md`）和读取服务那一节（7.1）。

### 7.1 渠道 Key 读取服务（开发 10-25 核过，依据 New API 源码 v1.0.0-rc.46）

| 要做到的 | 怎么做 | 前提、要注意的 |
|---|---|---|
| 读每个渠道填的 Key | 和 New API 放在同一个 docker compose 里的一个小服务，用 New API 同一套数据库环境变量（`SQL_DSN`：`postgres://` 开头是 PostgreSQL，否则是 MySQL；没有就是 SQLite，`SQLITE_PATH`，默认 `one-api.db`），每次只查一句：`SELECT id, name, type, key, channel_info FROM channels`。Key 在 `channels` 表的 `key` 列，明文；一个渠道几把 Key 时（`channel_info` 里 `is_multi_key`），`[` 开头的按 JSON 数组拆，否则按换行拆 | MySQL / PostgreSQL 建议另建一个只对 `channels` 有查询权限的账号，没有就用 New API 的账号（K 方案里列风险）。SQLite：New API 开的是 WAL 模式，读的一方也要能写 `-shm` 文件，所以数据卷不能只读挂载，改成小服务里用只读方式打开库 |
| 不交出完整的 Key | 只交：渠道 ID、渠道名、每把 Key 的打码（前 4 位、后 4 位）和 HMAC 指纹。算之前去掉 `sk-` 前缀和首尾空白，小服务和控制台用同一套规则（K 方案里写死），共用一把 HMAC 密钥，和登录信息一样加密存 | 有些渠道类型的「Key」不是一把 Key（例如 Vertex 的账号文件、AWS 的 `ak\|sk`）：不交，只记成「这类渠道不认 Key」（附录 7） |
| 和上游的 Key 精确比 | Sub2API：Key 列表给完整 Key，控制台在内存里算同一个 HMAC，算完就扔。New API（v0.11.4 起 Key 列表打码）：先按前 4 后 4 对；对出不止一把时，用 `POST /api/token/batch/keys` 取这几把的完整 Key 算 HMAC，算完就扔 | `batch/keys` 一次最多 100 把、限流严，所以只在有歧义时才调，不每轮调。New API v1.0.0-rc.41 起的新令牌（`nap_` 开头）要有 `api_key:reveal` 权限（附录 8） |
| 只给控制台读 | 走 HTTPS，带令牌（令牌的环境变量名在 K 方案里定），填进设置自营站点的抽屉 | 默认地址「站点地址 + 固定路径」要反向代理把这个路径转给小服务才通；没有反向代理、只用 compose 直接开端口的，在「更多设置」里填那个端口地址。「怎么装」里两种都写 |
| 搬服务器不用改控制台 | 它跟着你站的 docker compose 一起搬；你站的地址不变，控制台就不用改 | —— |
| 1 分钟内跟上换 Key | 控制台每分钟读一次，放进现有的结账轮询里，不另起定时器；返回内容的指纹没变就不写库、不重新比对，变了才处理变了的渠道 | 返回体每个渠道约 100 字节，1000 个渠道约 100 KB，不到被轮询接口 256 KB 的门槛（perf-baseline.md 第 8 节）；小服务那边一句查询，很轻 |
| 读不到时（例外三） | 连续 10 分钟读不到才进需处理。读不到的那几天用 C 的状态表标成「不能固定」，原因记「读不到渠道 Key」，不写账本，等 Key 确认了再定；这段时间上游的账单照样按旧 Key 读、照样显示，只是不算进汇总，所以连上以后 Key 没变时不用补读。Key 变了：读不到的那段时间单独成一段，段里放旧 Key、新 Key 两把，这段的成本是两把 Key 的账单相加，收入是渠道这段时间的收入（平时换 Key 那一分钟也是同一个办法，不多发请求）；只有一把 Key 在两个在算的渠道之间挪过时，走 C2b 的「改时间 → 按段重算」（和「改时间」同一条路），时间默认填重连的时刻。超过 7 天进需处理，和 C 的回看上限一致 | 要 C2a、C2b 先做完 |

放在哪个 PR（开发 10-25 定，K 方案里再细拆）：

- K1：小服务本身、读渠道 Key、换 Key 分段；
- K2：打码有歧义时取完整 Key、自动跟上换 Key；
- 第一次使用：「怎么装」、装好以后的连通检查。

### 7.2 其余（开发 10-25 已核）

| 读账号、余额 | 用令牌读账号信息和余额（现有） | 令牌有效 | 例外二 |
| 读 Key 列表（名字、分组、倍率） | New API `GET /api/token/`；Sub2API `GET /api/v1/keys` | Sub2API 只给名字和分组，读不到倍率 | Sub2API 上游只写到分组 |
| 确认每天的账单能读全 | 加上游时试读一次昨天的账单（现在「测试读取」做的事，改成自动） | New API 能按 Key 的名字取用量（Key 重名时报「上游有几把 Key 同名」，现有）；Sub2API 要能按 Key 取用量，而且认请求里带的时区（下一行） | 写「这个上游读不到每天的账单，只能看余额」，渠道照样列出、不能开始算利润（附录 5） |
| 定按哪个时区算一天 | 都按控制台的业务时区（部署时设定，所有页面按它算一天）：New API 的用量记录带到秒，自己切；Sub2API 按天的统计按请求里带的时区参数切天，控制台本来就带业务时区去请求，并核验过（现有） | Sub2API 要认这个时区参数 | 太旧、不认这个参数的 Sub2API 核验不过，按附录 5 处理，不另问时区 |
| 按 Key 算每天花的钱 | New API 按秒、按 Key 的名字取，已删的 Key 按名字还能取（Key 重名时报错，见上）；Sub2API 按天取，已删的 Key 查统计会报错，要翻明细或用总量减其他 Key | —— | 算好以前那几天写「还在读取」 |
| 登录过期时发现 | 读的时候被拒（现有） | —— | 例外二 |

两个渠道填了同一把 Key（第 1 节第 3 步）：现在就是这样算的（一把 Key + 几个渠道算一组）；K1 改成按渠道记的时候，要留住「同一段时间同一把 Key 的几个渠道算一组」，不然成本算两次（开发写进 K1 方案）。

已有的数据（一个账号分开加了几个上游）合并成一个上游：「上游类型 + 站点地址 + 账号 ID」三样都一样才算同一个账号（和现在判断同一个账号的办法一样）；同一个站点用了两个地址的，要人确认；读不出账号的（只填了 Key），照旧各是一个上游，按附录 1 显示（用户 10-25 定）。

摸底里还有一条要提前知道：New API 的 v1.0.0-rc.41 版起，旧的访问令牌在升级后满 30 天作废，要换带权限范围的新令牌。用户升级上游以后，可能一起碰到例外二。

## 8. 已定的 4 件（用户 10-25 定，都照推荐）

1. 合成以后的页签叫「渠道」。
2. 「绑定」这个词在界面上不再出现，用户看到的是「这个渠道在算利润 / 没算利润」，按钮是「开始算利润」「停止算利润」。
3. 「上游」就是一个账号（地址 + 令牌），已有的数据合并（第 7.2 节）。
4. 答过「只给我的渠道用」的上游，新连上来的渠道系统自己开始算（第 1 节第 3 步）。

## 附录：边角情况（不在正文里）

1. **只填了一把 Key、没有登录信息的上游**：系统只能读这把 Key 的余额和它自己的用量，读不到账号和别的 Key。渠道里填的就是这把 Key 时照样对得上。渠道换了别的 Key，新 Key 不在已加的上游里，走例外一；需处理那条的说明写「如果是这个上游换了 Key，在上游列表里改这个上游的 Key」。页面上写「这个上游只填了一把 Key，换 Key 时要来这里改」。改好以后，从换 Key 的时刻起按新 Key 读账单，中间那段（需处理的那几天）重算；旧 Key 换之前的账单早就读过了。
2. **账号不是只给你自己用**（答了「别处也在用」）：这个账号的钱也花在别处，系统读得出每个渠道用的是哪把 Key，但不知道这把 Key 有没有别处也在用。第 3 步里每把 Key 多问一句「这把 Key 还给别处用吗？」，五个选项照现在的（ui-copy-spec §5.2）：「只给这些渠道用」「站外也在用（测试、自用、给别人）」「别处也在用，说不清是哪」「不确定」（现在的第二项「自营站点的其他渠道也在用」新流程里不问：系统读得到你站所有渠道的 Key，同一把 Key 的渠道已经并成一行，一起算）。只有答「只给这些渠道用」的 Key 能直接算利润；站外也在用、说不清、不确定的，成本分不开，利润先不算，给渠道换一把单独的 Key 就能算。渠道换了 Key，系统照样跟上，但新 Key 要再回答一次：需处理里一条「这把 Key 还给别处用吗？」[去回答]，答之前那个渠道从换的时刻起先不算。第 3 步可以先点「开始算利润」再回答：没回答的那几把 Key 下的渠道先不算，需处理里各留一条 [去回答]。这两种上游下，新连上来的渠道系统不会自己开始算：需处理按上游一条「「上游名」下有 N 个新渠道还没算利润」[开始算利润]（总指挥 10-25 定）。渠道没在算，汇总就缺一块，所以提醒一次、给一个按钮；只给我的渠道用的上游，新渠道系统自己开始算，不出这一条。账号的问题答「不确定」：第 3 步照样能点「开始算利润」，但这个上游下的利润先不算，每把 Key 那一问也先不问，需处理里留一条「这个上游账号只给你自己的渠道用吗？」[去回答]。以后答了：答「只给我的渠道用」，从点「开始算利润」的时刻起补算（那段时间的账单一直照读）；答「别处也在用」，接着问每把 Key 那一句，答完一样补算。这两种上游下，新连上来的渠道不自己开始算。
3. **同一个上游网站有两个账号**：每个账号各加一次。渠道对哪个账号靠渠道里的 Key：Key 属于哪个账号就是哪个，分得清，不用你管。
4. **渠道用的 Key 不在已加的上游里，而且从来没开始算过**：这个渠道连的上游还没加。列在「渠道」页签最下面一组「没对上上游的渠道」，每行一句「这个渠道用的 Key 不在已加的上游里」[加上游]；渠道里填的地址对上了一个已加的上游、Key 却不在它的列表里的，也在这一组，写「这个渠道连的是「演示·主力账号」的网站，但用的 Key 不在这个账号里，可能是同一个网站上的另一个账号」[加上游]。都不进需处理；点了照例外一那样，地址按渠道里填的预先填好。官方渠道（直连模型厂商的）不在这一组里。
5. **上游读不到每天的账单**（版本太旧，或者账号没有权限）：加上游时写「这个上游读不到每天的账单，只能看余额」。第 3 步照样列出用它的 Key 的渠道，但不能开始算利润，那几行写同一句。
6. **你的站不是 New API**：自营站点只支持 New API，第 1 步读的时候写「自营站点要是 New API 站点」。
7. **渠道里填的不是一把 Key**（例如 Vertex 的账号文件、AWS 的 `ak|sk`）：读取服务不交这类渠道的 Key，系统认不了它用的是哪个上游。列在「渠道」页签最下面「没对上上游的渠道」里，写「这类渠道的 Key 系统认不了，利润算不了」，没有按钮，不进需处理。
8. **New API 上游的令牌少了读完整 Key 的权限**：只有两把 Key 的前 4 位、后 4 位刚好一样、要取完整 Key 才分得清时才用得上（第 7.1 节）。令牌没过期，只是少了一项权限（`api_key:reveal`）。
   - 不让人自己选是哪把，也没有「指定 Key」（用户 10-25 定：不用兜底），只请你给令牌补上这项权限：在上游后台给这个令牌勾上「读取完整 Key」（`api_key:reveal`），或者换一个带这项权限的令牌。
   - 还没开始算的渠道：第 3 步和「渠道」页签那一行写「这个上游的令牌少了读完整 Key 的权限，有两把 Key 分不清；给令牌补上这项权限就能算」[更新登录信息]，不能开始算，不进需处理。
   - 在算的渠道换成了这样一把 Key：需处理里一条「上游的令牌少了读完整 Key 的权限」（按上游出一条，不按渠道出），说明「有两把 Key 分不清，从 15:20 起这个渠道的上游成本算不出；给令牌补上「读取完整 Key」的权限，或者换一个带这项权限的令牌」，按钮「更新登录信息」（例外二同一个小窗）。
9. **自营站点不记收费记录了**（自营站点后台的一个开关；不记的时候渠道的收入读不到）。在哪里打开：系统设置 → 运维 → 日志维护 →「记录配额使用量」（旧版界面是：运营设置 → 日志设置 →「启用额度消费日志记录」）；开发 10-25 照 New API 各版本核过。
   - 第 1 步读到不记：不能开始算利润（照附录 5），写清原因和去哪里打开。
   - 今天不记：收入那几格照「读不到自营站点的收入」那一套写原因（ui-copy-spec §8.1），收入不写 0；需处理按站点一条「自营站点不记收费记录了」[重新检查]，读一次设置，在记了就消失。
   - 一天里只要读到过一次是不记的，这一天就不完整，不按读到的数固定。系统每 5 分钟读一次设置：两次读取之间关了几分钟又打开的，系统看不到，那几分钟的收入会算少。
   - **没记的那几天怎么收尾（用户 10-25 定）**：那几天一直是需处理、利润写「—」、不固定、不算进汇总，原因写在那几天自己身上（「这一天自营站点有一段没记收费记录，那段的收入补不回来」），没有按钮，也不进需处理清单；清单里只在现在还不记时列那一条。已知少算的数不混进汇总，合计永远是能对上的数。这是需处理里唯一没有按钮的一种（ui-copy-spec §4）。
10. **自营站点的令牌读不到设置**（账号不是超级管理员——自营站点的设置只有 root 读得到——或者新式令牌少了「读设置」的权限 option:read）：照常读、照常算收入，只在原处写一句（设置自营站点抽屉的令牌下面、上游列表里自营站点那一行），不进需处理、不推送，和附录 4–7 一样。少了这项本身不会把数算错，只是发现不了附录 9。以后要不要进需处理，等 E 改稿时和「固定成本上游的 Key 坏了怎么提醒」一起问用户。

# 界面用语规范

> 界面上出现的每一个字都按本文写：页面、按钮、提示、弹窗、表头、报错、导出文件、告警推送、日报。
> 本文是唯一来源。[ui-design-spec.md](./ui-design-spec.md) §6 只指向这里；代码里的文案表只放在 §12 列出的几处，并由测试守住。
> 2026-10-16 起草，已对照全站用语排查（258 处）补全；2026-10-16 确认（含 §11 的改名、「花费 / 上游成本」分工、「测试连接」并入「测试读取」）。

## 1. 写给谁看

用的人是财务、运营、客服，不是写代码的人。他们懂收入、成本、利润、对账，但不知道系统内部怎么取数、怎么判定。

所以每一句话只需要回答三件事：

1. 这个数**能不能信**？
2. 要不要**我动手**？
3. 动手的话**点哪里**？

系统内部做了什么（重试、快照、版本、判定规则、接口、请求头）一律不说。

## 2. 七条原则

1. **先说对钱的影响，再说怎么办。**不说系统里发生了什么。
   - 对：「这把 Key 还给别处用吗？回答之前，利润先不算。」
   - 错：「消费范围待确认，金额仅供参考。」
2. **一个东西只有一个名字。**全站一致，包括按钮、提示、报错、推送和日报。名字见 §3。
3. **不出现后台用语。**英文代码、字段名、内部状态名、接口路径、HTTP 状态码和 §3.6 的词一律不上界面。数据里带着未知代码时，按 §5.5 显示，不把代码本身露出来。
4. **专业词只在要填写的地方出现。**例如站点地址、访问令牌、Webhook 地址，并且下面配一行白话说明（§3.7）。
5. **正常时不标。**「数据正常」「已核验」「有效」这类标签不显示，只在不正常时才说话。
6. **不确定就直说。**用「≈」「还在读取」「—」加一句原因，不用红色吓人，也不把估算当成准数。
7. **按钮用动词开头，同一个动作从头到尾一个名字。**按钮叫「重新读取」，完成提示就写「已重新读取」，弹窗标题也叫「重新读取」。

## 3. 词表

### 3.1 东西叫什么

| 用这个词 | 意思（可以直接用作界面上的说明文字） | 不再用 |
|---|---|---|
| 上游 | 你采购额度的地方；列表页叫「上游资源」，说某一个或几个时叫「上游」 | 站点、中转站、资源（单独用时）、监控站 |
| 上游账号 | 你在某个上游的登录账号。下拉里选上游时写「上游名 · 账号 42」，暂停监控的再加「 · 暂停监控」，不写类型名 | 账号身份、原始身份、稳定身份 |
| Key | 上游发给你的调用密钥，显示为 `sk-…abcd`。列表和下拉里写 Key 的名字；没有名字时写「Key #34」；同一个页面里两把 Key 同名时，两把的名字后面都加「（Key #34）」区分。一个页面里出现的 Key 放在一起比：上游账单比各账号下的 Key，渠道绑定比读到的 Key 和已有的绑定 | 令牌、实际 Key、canonical Key、sk 密钥 |
| 自营站点 | 你自己运营、卖给用户的站点 | 本站、我的站点、我的中转站、本站管理员站点、自营资源、自营业务站点、NewAPI 管理员站点 |
| 渠道 | 自营站点里的一条供货线路 | 销售渠道、本站渠道、上游渠道 |
| 绑定 | 一把 Key 和自营站点里几个渠道的对应关系；有了绑定才能算利润 | 核算关联、关联、范围、来源绑定 |
| 看余额 / 算利润 | 渠道绑定时对一个上游要做的两件事：「看余额」只读余额、发余额提醒；「算利润」绑定 Key，每天算利润。至少选一个，没选时写「请选「看余额」或「算利润」」，下面再写一句「「看余额」只读余额、发余额提醒，不用选 Key；「算利润」要选 Key，每天算利润」。只用 Key 的上游只能看余额 | 接入监控、对账、核算、监控与对账 |
| 在用 / 已解除绑定 | 一条绑定现在还算不算利润；在「以前的每日记录」里选绑定时标在名字后面 | 生效中、已停用、已归档 |
| 没对上上游的渠道 | 渠道里填的地址找不到对应的上游。和「绑定」是两回事 | 未关联上游资源的渠道、未直接关联监控站 |
| 渠道里用的其他地址 | 渠道里填的不是上游的公开地址时（内网地址、代理地址），把那个地址填在上游里，才对得上 | 成本渠道匹配别名 |
| 分组 | 上游里的价格档位 | 分组目录 |
| 只走一个分组 / 失败自动换分组 | Key 的两种分组设置。只有「只走一个分组」的 Key 能绑定 | 固定分组、跨组重试 |
| 倍率 | 上游对一个分组收的价格倍数；细分时写「模型倍率」「分组倍率」「输出倍率」 | 路由、计价倍率、模型× |
| 用量记录 | 上游记下的每次调用和扣费 | 消费日志、账单证据、计量 |
| 收费记录 | 自营站点记下的向用户收费 | 渠道账单统计、本站收费流水 |
| 每日记录 | 每天定下来的那一行利润 | 结账记录、账本、快照、已确认账单 |
| 固定成本记录 | 固定成本的一笔：金额加天数 | 付费记录 |
| 登录信息 | 系统读取上游或自营站点用的访问令牌、登录令牌、用户 ID、密码、Key 的统称 | 凭证、凭据、连接凭证、授权、账号授权 |
| 超级管理员 | 自营站点里权限最高的账号 | root、管理员（root）、role ≥ 10 |
| 转售 Key | 用管理员账号开出来卖给客户的 Key，它的花费算收入 | 管理员转售 Key、管理转售 Key、转售的管理员 Key |
| 管理员自用 | 管理员自己在自营站点里用掉的额度，不算收入 | 管理员消耗、root 自用 |
| 历史数据 | 系统定时记下的余额和花费，不是每次调用的明细 | 监测历史、原始快照、监测快照、采集数据 |
| 通知方式 | 告警发到哪里：Telegram、钉钉、邮箱等 | 渠道、通知渠道、发送渠道（在告警中心里） |
| 已登录的设备 | 当前登录着这个控制台的浏览器 | 会话 |
| 软件版本 | 这套控制台的版本号 | 构建标识 |

### 3.2 钱叫什么

| 用这个词 | 怎么算 | 不再用 |
|---|---|---|
| 收入 | 自营站点向用户收的钱，来自收费记录 | 本站收费、期内收入、销售额 |
| 上游成本 | 上游按用量扣的钱，来自用量记录。包月或按期付费的上游在这一格写「计入固定成本」，数字记 0 | 用量成本、消耗、消费、已计入上游成本 |
| 固定成本 | 按月或按期付的钱（服务器、包月上游等），按天平摊 | 固定付费、固定采购、月费、摊销 |
| 毛利 | 收入 − 上游成本 | 利润（单独用时）、账面毛利、已确认毛利 |
| 净利 | 毛利 − 固定成本 | 净利润 |
| 毛利率 / 净利率 | 毛利 ÷ 收入 / 净利 ÷ 收入 | —— |
| 亏损 | 毛利或净利小于 0 时，数字旁的标签 | 负毛利 |
| 没算进利润的上游成本 | 上游账号实际扣的钱，减去已经算进各条绑定的部分。没有绑定的 Key、测试和自用都落在这里 | 未纳入核算的上游消费 |
| 算进利润 / 不算进利润 | 上游上的开关：这个上游的花费要不要算进利润 | 计入利润成本、不计利润成本、不计入利润 |
| 汇率 | 写成「1 美元 = 7.20 元」。没设置时的写法见 §7 | 换算比例、FX、1:1、$1 = ¥2、充值折算汇率 |
| 售价 | 给用户充 1 美元额度收多少元，写成「1 美元额度 = 7.50 元」，和汇率分开 | 售价汇率 |
| 预收 | 用户已经付了钱、还没用掉的余额 | 用户余额合计 |

没算进利润的上游成本算出来小于 0（已算进利润的比上游实际扣的还多）时，金额照实显示负数，旁边说明原因，只用这三句：

- 「已算进利润的多于上游扣费：上游的扣费可能还没记全」
- 「已算进利润的多于上游扣费：两边汇率不同」
- 「已算进利润的多于上游扣费：上游的扣费可能还没记全，两边汇率也不同」

「利润」只作统称，用在标题或句子里，例如「算利润」「利润暂时算不出」。具体的数字必须写明是毛利还是净利。

「消费」只用来说自营站点的用户花了多少（例如「消费最多的用户」），不用来说上游。

### 3.3 余额和提醒

这一组只用在看余额、提醒、可用天数的地方。

| 用这个词 | 意思 | 不再用 |
|---|---|---|
| 余额 | 上游账号里还剩的钱，按上游自己的币种显示（`$` 或 `¥`） | 站点余额、剩余额度 |
| 花费 | 余额减少了多少。只用在余额相关的地方：「今天花费」「日均花费」「花费时段」 | 消耗、消费、日均消耗 |
| 可用天数 | 余额 ÷ 日均花费，写成「可用约 3 天」 | 跑道、余额跑道、预计耗尽 |
| 余额提醒线 | 余额低于这个数就提醒；单个上游可以另填 | 阈值、告警阈值、低余额阈值、全局阈值 |
| 余额偏低 / 快用完 / 余额用完 | 余额只有这三档。「快用完」后面跟「可用约 N 天」 | 耗尽、已耗尽、即将耗尽、耗尽预警 |
| 按用量算 / 按余额变化估算 / 固定成本 | 一个上游的成本是怎么来的 | 余额推算、按余额历史推算、固定摊销、回归 |
| 按天平摊 | 固定成本每一笔 = 金额 ÷ 天数 | 摊销、按天摊销、摊分 |
| 不再续费 | 固定成本到期后不再续 | 续费计划 |
| 归档 | 不再刷新和提醒，历史数据保留 | —— |
| 暂停监控 | 先不刷新这个上游的余额，随时可以恢复 | 监控暂停、未启用 |

「上游成本」和「花费」不混用：算利润的地方说上游成本，看余额的地方说花费。

### 3.5 动作叫什么

同一个动作，按钮、弹窗标题和完成提示都用同一个名字。

| 按钮 | 用在哪 | 完成提示 | 不再用 |
|---|---|---|---|
| 去绑定 | 渠道还没绑定 Key；进入绑定流程，最后一步按钮叫「确认绑定」 | 已绑定，从现在开始算利润 | 接入这些渠道、建立核算关联、接入监控与对账 |
| 改绑定 | 改一条绑定里的渠道；渠道绑定里，已经看余额或算利润的渠道按钮也叫这个 | 已保存 | 编辑范围、修改关联、管理关联 |
| 接着做完 | 渠道绑定保存到一半（有几步没做完），回来接着保存剩下的；做完的部分保留 | 还有几步没做完，做完的会保留 / 全部做完时同「去绑定」 | 继续完成、重试未完成步骤 |
| 用已有上游 / 新增上游 | 渠道绑定里选一个已保存的上游，或者填一个新的 | —— | 复用已有上游、新增上游账号、返回复用已有上游 |
| 用已保存的 | 填的登录信息和一个已保存的上游账号是同一个，改用已保存的那个；要换登录信息就点「更新登录信息」 | —— | 复用此账单账号、复用这个账号 |
| 换 Key | 一条绑定换成新 Key | 已换成新 Key，旧 Key 以前的每日记录还在 | 停止旧 Key 核算后重新关联 |
| 解除绑定 | 不再算这把 Key 的利润 | 已解除绑定，以前的每日记录还在 | 停止核算、归档关联 |
| 测试读取 | 确认能读到上游的余额或账单。上游编辑页和需处理里都用这个名字 | 能读到余额 $123 / 能读到账单 / 能读到这个上游（只确认连得上、没重新读余额时）/ 读不到：原因 | 测试连接、核验账号身份、核验账单能力、验证、核对 |
| 更新登录信息 | 上游或自营站点的登录信息过期、被拒 | 已更新登录信息 | 更新账号授权、更新 PAT、重新登录上游 |
| 重新读取 | 某一天的账单没读全或读不到 | 已重新读取 | 重查该窗口账单、补结、重新结账 |
| 去回答 | 回答「这把 Key 还给别处用吗？」 | 已保存 | 核对这把 Key 的全部用途、确认消费范围 |
| 去确认 | 上游账号或自营站点有变化，需要确认 | 已确认 | 核对本站来源、确认新范围 |
| 处理重复 | 一把 Key 绑了两次，或一个渠道绑了两把 Key | 已处理 | 处理重复归属 |
| 改时间 | 修改倍率变化的时间 | 已修改，受影响的日子已重算 | 修正切换时间、确认分段 |
| 刷新 | 重新读一遍当前页面或某个上游的余额 | 已刷新 | 同步、重读、重试、重新拉取、重试发现 |
| 查看余额 | 去看上游余额 | —— | 查看余额与监控 |
| 暂停监控 / 恢复监控 | 上游账单里，暂时不刷新某个上游的余额；绑定照常算利润。渠道绑定里选到暂停的上游时写「这个上游暂停了监控，恢复后就能看余额。」，按钮「恢复监控」，确认框标题「恢复监控「上游名」？」 | 已暂停监控，绑定照常算利润 / 已恢复监控 | 停用监控、启用监控、启用此资源监控 |
| 查看详细原因 | 展开给技术同事看的原文（§8.2） | —— | 查看脱敏诊断、诊断信息 |
| 去设置 | 还没设置自营站点（§8.1），去上游资源里打开「这是我的自营站点」；没设置汇率时也用它，去上游资源里填汇率 | —— | 前往配置 |
| 以前的每日记录 | 打开「以前的每日记录」区块；按钮名和区块名同一个 | —— | 已确认账单历史、查看历史 |
| 开始细算 | 按明细细算 | —— | 开始精算、重新精算 |
| 添加通知方式 / 删除通知方式 | 告警中心 | 已添加 / 已删除 | 添加渠道、删除渠道 |
| 删除上游 | 连同历史数据一起删；确认时输入这个上游的名字 | 已删除 | 彻底删除资源、输入 DELETE |

「算利润」是对外的统称，用在句子里，例如「有了绑定才能算利润」，不单独做按钮。

渠道绑定里，已经看余额的渠道改上游时问「看余额怎么改」，四个选项：不改 / 加上游 / 换上游 / 去掉上游。预览按渠道写「不变：…」「加上：…」「去掉：…」，要去掉的上游写成「去掉「上游名」」让人勾选。不写「解除监控」「更换监控」「保留现有监控」。

### 3.6 不上界面的词

这些词说的是系统内部怎么做，不是用户关心的事。左边的词在界面上一个都不出现，要说的话按右边改。

| 不用 | 改成 |
|---|---|
| 英文代码和字段名，例如 READY、PENDING、BILLING_*、health、scope、window、segment、ruleId、quota、access_token、null、undefined、NaN | 按 §5、§8 的对照表说人话 |
| 接口路径、请求头、HTTP 状态码，例如 /api/user/self、Authorization、New-Api-User、401、DataExportEnabled | 不说；必要时放进「详细原因」 |
| CNY、USD、原币 | `¥`、`$`；要说币种时写「美元」「人民币」 |
| 核算、核算关联、关联（指绑定时）、范围、覆盖、归属 | 绑定；「已算进利润」「没算进利润」。页面名改为「每日利润」后（§11），「核算」不再出现 |
| 结账、已结账、待结账、自动结账、补结、重新结账 | 已固定、过了零点自动固定、重新读取 |
| 窗口、区间、自然日、等长窗口、上窗 | 这天、这几天、10月1日–10月7日、上期 |
| 分段、切换、路由变化 | 倍率在 14:30 变了 |
| 生效、生效时间、生效前、范围未生效、待生效 | 从 10月9日 14:30 开始统计；还没开始 |
| 范围版本、计算版本、授权版本、配置版本、第 N 版 | 不显示；改过的只标「改过」 |
| 口径、金额口径、计法、成本计法 | 「怎么算的」「计算明细」，用白话说（§9） |
| 证据、能力、原始身份、稳定身份、命名空间、namespace、PAT、JWT | 测试读取；上游账号；登录信息 |
| 核验、验证、核对（三个词混用） | 测试读取（检查能不能读到）、确认（让用户拍板） |
| 凭证、凭据、授权（指登录信息时） | 登录信息。「凭证」在财务里是记账凭证，不能用 |
| 仅供参考、金额参考、参考差额、风险差额 | 需处理加一句原因，利润写「—」 |
| 待获取、获取中、不可用、读取失败、查询失败、尚未查询（作状态） | 读取中、没读全、读不到、还没读取 |
| 数据已过期、当前显示上次结果、最新数据获取失败 | 刷新失败，数据截至 14:30 |
| 最后刷新、更新于、最近成功、最近检查、最近同步、结果生成、读取时间 | 数据截至 14:30 |
| 快照、账本、迁移、旧账、兜底、降级、轮询、采集、留存、重试次数 | 不说；必要时说「历史数据」「以前的数据」 |
| 目录、发现（指读取渠道列表时） | 渠道列表；刷新 |
| 回归、回测、精算、推算、预测方法 | 按余额变化估算、预测准不准、按明细细算 |
| 中转站、本站、资源（单独用时）、站点（指上游时） | 上游、自营站点 |
| 阈值、耗尽、消耗、摊销 | 余额提醒线、用完、花费、按天平摊 |
| 同步、重读、重试（作按钮） | 刷新、重新读取 |
| 待办、待处理、待核算 | 需处理 |
| 数据正常、已核验、有效、完整、已取全 | 不标 |

### 3.7 只在填写处出现的专业词

下面这些词用户在别的后台见过，填写时也必须认得，所以保留原词。但每个都要配一行白话说明，放在输入框下方。说明只写「去哪里找、怎么复制」，不写接口和原理。

| 输入框名称 | 输入框下方的说明 | 不再用 |
|---|---|---|
| 站点地址 | 上游网站的地址，例如 `https://api.example.com` | 账单站点地址、面板地址 |
| Key | 在上游后台的「令牌」或「API 密钥」页面复制，以 `sk-` 开头 | API 密钥、上游 API Key（作输入框名时） |
| 访问令牌 | 在上游后台「个人设置」里生成，用来读取余额和用量记录 | PAT、系统访问令牌、账单授权、账号账单授权 |
| 登录令牌 | 登录 Sub2API 后拿到的一串字符，用来读取余额和用量记录 | JWT（放到说明里也不写） |
| 用户 ID | 上游后台「个人设置」里的数字 ID；上游要求时才填 | New-Api-User |
| 登录邮箱 / 登录密码 | 你在上游登录用的邮箱和密码 | 账密 |
| 时区 | 按哪个地方的 0 点算一天 | 账单时区 |
| 两步验证 / 数据看板 | 对方后台里的开关名，照原名写，不加括号英文 | 2FA、DataExportEnabled |
| 通知方式的填写项 | Webhook 地址、Bot Token、Chat ID、加签密钥、SendKey、SMTP 服务器、端口等保留原名，说明写「在 Telegram / 钉钉 / 邮箱设置里能找到」 | —— |

上游类型只用一张表：

| 类型 | 说明 |
|---|---|
| New API 账号 | 用访问令牌读取余额和账单 |
| New API Key | 只用一把 Key 读取余额 |
| Sub2API 账号（登录令牌） | 用登录令牌读取 |
| Sub2API 账号（邮箱密码） | 用邮箱密码登录，自动续期 |
| 固定成本 | 不读取上游，只记固定成本 |

句子里说到「New API Key」这一类时，写「只用 Key 的上游」，不写「独立 Key」。

New API、Sub2API 只出现在选择类型的地方，别处不用。

## 4. 每天只有三种状态

每条绑定的每一天，在界面上只会是下面三种之一。

| 状态 | 什么时候 | 怎么显示 |
|---|---|---|
| 实时 | 今天，数字还会变；或者过去某天系统还在自动重读（最多 7 天） | 「实时」，旁边写「数据截至 14:30」；过去的日子再加一句「还在读取」 |
| 已固定 | 过去的日子，数字定下来了，不会再变 | 「已固定」；鼠标悬停写「10月10日 0:05 固定」 |
| 需处理 | 不处理就算不准，需要有人动手 | 「需处理」，加一句原因和一个按钮，利润写「—」 |

判定顺序：

1. 有不处理就算不准的问题，就是**需处理**。
   - 只显示最要紧的一条，其余收起成「还有 2 个问题」。
2. 否则，这天已经定下来了，就是**已固定**。
3. 否则就是**实时**，可以带一句提示，例如「还在读取」「从 14:30 开始统计」「倍率在 14:30 变了」。

两条补充：

- **读不到账单这类问题**，系统会自己重读，所以先不算需处理：
  - 今天：显示为「实时」加提示。
  - 过去的日子：系统自动重读的 7 天里显示「实时」和「还在读取」；7 天后还没读到，才变成「需处理」。
- **不影响结果的事不改变状态**，只在对应位置加一个小标签或一句提示：
  - 渠道停用，在渠道名旁标「已停用」。
  - 倍率变了，加一句提示。
  - 统计开始时间，写「从 X 开始统计」。

其他标签只允许这几个：

- 「改过」：已固定的日子后来被重算过。
- 「亏损」
- 「已停用」「已删除」：只用在渠道上。
- 「≈」：估算。

多天合计的写法：

- 都定下来了：「7 天已固定」。
- 混合：「6 天已固定，今天实时」。
- 有需处理的日子：照常显示其余日子的合计，旁边写「其中 2 天需处理，没算进来」。

改设置时，保存前提示一句：「今天按新设置重算；以前还没固定的日子先按原设置固定，不受影响。」如果有的日子没能固定，保存后提示「有 2 天没能固定，已放进需处理」。

## 5. 问题怎么说

### 5.1 一条问题的写法

```
[需处理]  标题：一句话说发生了什么（用户的话）
          说明：对利润的影响 + 怎么办（可省略）
          [按钮]                还有 2 个问题 ▾
```

- 标题不超过 20 个字，不带句号。
- 说明一句话。原因已经能看懂时，说明可以省略。
- 只放一个按钮，名字来自 §3.5。
- 同一条绑定有多个问题时，只露出最要紧的一条，其余收起。

### 5.2 需处理（不处理就算不准）

系统码那一列只给开发看，界面上不显示。

| 标题 | 说明 | 按钮 | 系统码（开发用） |
|---|---|---|---|
| 上游拒绝读取这把 Key | Key 可能已被删除，或上游的登录信息过期了 | 更新登录信息 | KEY_INVALID_OR_DENIED |
| 上游账号或自营站点有变化 | 确认这条绑定还对应原来的账号和渠道，利润才会接着算 | 去确认 | SOURCE_BINDING_UNCONFIRMED |
| 还没确认这把 Key 属于哪个上游账号 | 测试读取一次就好 | 测试读取 | COST_OWNER_UNVERIFIED、LEGACY_IDENTITY_UNVERIFIED |
| 还没确认能读到这个上游的完整账单 | 测试读取一次就好 | 测试读取 | UPSTREAM_CAPABILITY_UNVERIFIED |
| 还没确认这个上游按哪个时区算一天 | 测试读取一次就好 | 测试读取 | BILLING_TIMEZONE_UNVERIFIED |
| 这把 Key 绑了两次 | 同一把 Key 的上游成本只能算一次，去掉多余的那条 | 处理重复 | CANONICAL_KEY_CONFLICT |
| 渠道「X」同时绑了两把 Key | 同一个渠道的收入只能算一次，去掉多余的那条 | 处理重复 | DUPLICATE_CHANNEL_ASSIGNMENT |
| 这把 Key 还给别处用吗？ | 别处也在用的话，上游成本会算多；回答之前，利润先不算 | 去回答 | COST_COVERAGE_UNKNOWN |

「去回答」的选项：

| 选项 | 系统值（开发用） |
|---|---|
| 只给这些渠道用 | none |
| 自营站点的其他渠道也在用 | other_use + own_channels |
| 站外也在用（测试、自用、给别人） | other_use + external |
| 别处也在用，说不清是哪 | other_use + unspecified |
| 不确定 | unknown |

不是由某个问题引出的事项（运营总览、上游账单的「需要处理」里用）：

| 标题 | 说明 | 按钮 |
|---|---|---|
| 登录信息不对或过期了 | 更新之后才能接着读取余额和账单 | 更新登录信息 |
| 有 3 个渠道还没绑定 | 绑定之后才能算这些渠道的利润 | 去绑定 |

### 5.3 读取类（系统会自己重读，规则见 §4）

| 实时时的提示 | 7 天后变成需处理时的标题 | 按钮 | 系统码（开发用） |
|---|---|---|---|
| 读取中 | 这天的账单一直没读到 | 重新读取 | PENDING |
| 这天的账单还没读全 | 这天的账单一直没读全 | 重新读取 | WAITING_FOR_BILL |
| 上游暂时读不到，系统会自动再读 | 上游这天的用量记录一直读不到 | 重新读取 | UPSTREAM_DATA_UNAVAILABLE |
| 自营站点暂时读不到，系统会自动再读 | 自营站点这天的收费记录一直读不到 | 重新读取 | OWN_BILLING_UNAVAILABLE |
| 读到的日期和这天对不上，系统会再读 | 读到的日期一直和这天对不上 | 重新读取 | BILLING_WINDOW_MISMATCH（上游、自营站点哪一侧对不上都用这一行，所以不写「上游」） |
| 有收入，但上游的用量还没到 | 有收入，但上游一直没有用量记录；可能绑错了 Key | 改绑定 | UPSTREAM_EMPTY_WITH_SALES |
| 这次结果没存上，系统会再存 | 这天的结果一直没存上 | 重新读取 | PERSISTENCE_FAILED |

实时状态下如果读不到：

- 有上次读到的数字，就显示它，并写「数据截至 14:30」。
- 没有，就写「—」。

### 5.4 提示类（不改变状态，可以不管）

| 怎么显示 | 按钮（可选） | 系统码（开发用） |
|---|---|---|
| 不显示 | —— | READY |
| 一句提示「倍率在 14:30 变了，这天分两段算」 | —— | ROUTE_TRANSITION_DETECTED |
| 一句提示「倍率变化的时间是系统估的」 | 改时间 | SEGMENT_TIMING_UNCONFIRMED |
| 改过时间后，一句提示「倍率变化的时间是手动改的」（不写「改过」，「改过」只说已固定的日子又重算过，§4） | —— | 人工改过的倍率变化时间 |
| 一句提示「从 10月9日 14:30 开始统计」；不知道从什么时候开始时写「还没开始统计」 | —— | BILLING_SCOPE_NOT_EFFECTIVE |
| 渠道名旁标「已删除」，再加一句「渠道「X」在自营站点里已删除，不用了就从绑定里去掉」 | 改绑定 | SALES_CHANNEL_MISSING |
| 渠道名旁标「已停用」 | —— | SALES_CHANNEL_DISABLED |
| 不显示 | —— | SALES_CHANNEL_STATE_UNKNOWN |
| 倍率格写「暂时读不到」 | —— | GROUP_DATA_UNAVAILABLE |
| 包月上游的上游侧问题不显示 | —— | 带参考标记的问题 |
| 汇总（和每组小计）下写一句「上游成本没算进来的绑定：Key A、Key B。」，绑定已解除的写「已解除的绑定」 | —— | 汇总里的 notCountedCostRuleIds（例如和别的绑定共用一把 Key） |

### 5.5 删除和兜底

**删除。**下面这些码现在不会再产生，界面文案一并删除：

- STALE
- GROUP_OR_RATIO_CHANGED
- BILLING_WINDOW_UNCONFIRMED
- OWN_FLOW_INCOMPLETE

以前的数据里如果还带着这些码，统一显示为「这天的数据不完整」，归读取类处理。

**名字找不到时。**上游已经删掉的写「已删除的上游」，提示里要点名时写「已删除的上游（编号）」；Key 和渠道没有名字时按 §3.1 写「Key #34」「渠道 #12」。

**兜底。**遇到表里没有的码时：

- 显示「需处理：这条暂时算不出利润」和「刷新」按钮。
- 码本身只写进浏览器控制台，界面、推送和日报上都不显示。

### 5.6 渠道列表里的状态

| 显示 | 意思 | 不再用 |
|---|---|---|
| 已算进利润 | 这个渠道的收入算进了利润 | 已核算、已关联 |
| 没绑定 | 还没和任何 Key 绑定，加上「去绑定」 | 未关联、尚未建立核算关联 |
| 从 X 开始统计 | 绑定是这之后才建的 | 范围未生效 |
| 需处理 | 原因按 §5.2 说 | 来源待核验、Key 用途待确认、重复归属、待重新确认 |
| 还在读取 | 按 §5.3 说 | 账单未齐、该窗口账单证据尚未读取 |
| 只看余额 | 这个上游只看余额，不算利润 | 仅监控 |
| 读不到账单 | 这个上游不支持读取账单，只能看余额 | 账单能力不支持、暂不可用 |

渠道绑定里一个渠道只显示一种状态：要重新确认的先写「需处理」，再看算没算进利润、是不是只看余额，都不是就写「没绑定」。状态筛选的选项就是这几种：「全部渠道」「需处理」「没绑定」「只看余额」「已算进利润」，选哪种就列出显示哪种的渠道。

汇总写成「5 个渠道里 4 个已算进利润」，后面跟「查看没算进来的」。不用「已知渠道覆盖：已核算 4/5」这种写法。

## 6. 时间

| 场景 | 写法 |
|---|---|
| 数据时间 | 当天写「数据截至 14:30」；不是当天写「数据截至 10月9日 14:30」 |
| 日期 | 今年写「10月9日」，往年写「2025年10月9日」 |
| 一整天 | 只写日期「10月9日」，不写「00:00 – 次日 00:00」 |
| 日期范围 | 「10月1日–10月7日」，同月也写全两个日期 |
| 时刻 | 24 小时制「14:30」，不写秒 |
| 时区 | 一律按业务时区显示，包括推送、日报和日报发送时间。只有和业务时区不同时才写，例如「按 UTC 时间算一天」 |
| 一天 | 业务时区的 0:00 到 24:00；界面上不解释，只在设置页说明一次 |

界面上禁止出现 ISO 格式（`2026-10-09T06:30:00.000Z`）、`YYYY-MM-DD`、时间戳数字、时区代码（`Asia/Shanghai`），以及「窗口」这个词。

## 7. 数字和金额

格式规则以 [ui-design-spec.md](./ui-design-spec.md) §4.5 为准，那里的币种一行按下面更新：

- 金额按系统里的原始币种显示（美元写 `$214.30`）。只有设置了汇率才换算成人民币，换算处标「按 1 美元 = 7.20 元换算」。
- 「每日利润」页没设置汇率时不折算，写「没设置汇率，按美元显示」。
- 运营总览、上游资源、成本估算、自营业务这几页目前没设置汇率时仍按 1 比 1 折算，文案照实写「没设置汇率，暂按 1 美元 = 1 元算」。要不要改成不折算，另外决定，不在本次范围。
- 余额按上游自己的币种显示，推送里也一样，不一律写 `$`。

另外四条：

- 不知道的数写「—」，旁边或悬停写原因。不写 0、不写空白、不写 NaN。
- 估算值前加「≈」，后面跟一句为什么是估算。
- 亏损的数字仍用墨色，前面用真正的减号「−」，旁边标「亏损」。
- 笔数写「3 笔在用，1 笔还没开始」，不写「生效 3/4 笔」。
- 很小的金额最多写到 8 位小数；小到 8 位小数也是 0 的，按三位有效数字写成小数（`$0.00000000123`），不写成 0，也不写科学计数 `1e-9`。

## 8. 空、加载、出错

### 8.1 页面状态

| 场景 | 写法 |
|---|---|
| 首次加载 | 骨架屏，不写字 |
| 没有数据 | 一句说明加一个按钮，例如：「还没有绑定。把上游的 Key 和自营站点的渠道绑定后，这里每天算一次利润。」[去绑定] |
| 还没设置自营站点 | 「还没设置自营站点：在上游资源里编辑你的 New API 站点，打开「这是我的自营站点」。」[去设置] |
| 没有需处理的事 | 「没有需要处理的事。数据截至 14:32。」不知道数据时间时只写前一句 |
| 刷新失败但有旧数据 | 「刷新失败，数据截至 14:30。」[刷新]。从来没读到过时只写「刷新失败」 |
| 读不到自营站点的渠道 | 一次都没读到：「读不到自营站点的渠道：原因。」[刷新]；读到过：按上一行写 |
| 一次选的渠道太多或没选 | 「一次选 1 到 100 个渠道」「请至少选一个渠道」 |
| 整块读不到 | 「读不到上游账单：原因。」[刷新]。每日利润、以前的每日记录、绑定列表整块读不到时同样写「读不到每日利润：原因。」 |
| 操作失败 | 「保存失败：原因。」原因按 §8.2 写，并说下一步 |
| 单条「重新读取」没成 | 「重新读取没完成，请稍后再试」[查看详细原因] |
| 以前的每日记录 | 区块下写一句「每天固定后不会再变，也不算进上面的汇总。默认看最近 31 天，一次最多查 31 天。」 |
| 需处理的事已经变了 | 「这条已经变了，刷新后再看。」[刷新] |
| 数据隔太久没更新 | 「数据截至 14:20，已经 10 分钟没更新。」[刷新] |

出错文案不道歉，不写「出错了」「未知错误」「服务器错误」这类空话。

### 8.2 报错只说这几类

服务器、上游、自营站点返回的报错原文不上界面。先归到下面一类，界面上只写这一类的话；原文放进「详细原因」。

| 哪一类 | 界面上写 | 下一步按钮 |
|---|---|---|

- 默认收起，链接写「查看详细原因」，展开后是原文和一个「复制」按钮，标题写「发给技术同事看」。

- 原文里的密钥、令牌照旧打码。

## 10. 推送和日报

推送和日报用和页面一样的词，在发送的代码里直接写成最终文字，不再发送前用替换改写。

只推余额提醒；什么时候推的规则不变，只改用语。每日利润的需处理不单独推送，写进日报的一行里（见下面「日报」）。

**标题**

| 什么时候 | 标题 |
|---|---|
| 余额偏低 / 余额用完 / 读不到余额 | 【炬元告警】上游名 余额偏低 |
| 快用完 | 【快用完】上游名 可用约 3 天 |
| 持续没处理 | 【持续告警】（不变） |
| 恢复 | 【恢复通知】（不变） |
| 日报 | 【炬元日报】（不变） |

**正文**每行写「名称：内容」，只用下面这些名称：

- 余额推送：上游、状态、余额、日均花费、可用天数、原因、时间。
  - 例：「余额：$12.30」「日均花费：$4.10，可用约 3 天」「原因：登录信息过期了」「时间：10月9日 14:30」。

**日报**里的词：收入、管理员自用、上游成本、毛利、预收、用得最多的模型、消费最多的用户、预计花费（「预计 $30 到 $40，按过去 14 天估算，过去 2 周平均差 ±8%」）、「统计的是 10月9日 一整天」、「还没有上游」、「还没读取」、「没读到（登录信息过期了）」。

日报里每日利润只写一行，条数和页面「需处理」区块的条数来自同一份列表：

- 有要处理的：「每日利润：有 3 条需处理」，下一行「去处理：链接」，链接打开「每日利润」页。
- 没有要处理的：「每日利润：没有需处理的」，不带链接。
- 没配置控制台地址时，「去处理：」后面写「打开炬元控制台的「每日利润」页」。
- 读不到时：「每日利润：没读到（原因）」，原因按 §8 归类。

5. **推送和日报按 §10 写。**
6. **测试守住。**
   - 每个问题码、动作、报错类别都有文案。
   - 文案表里没有 §3.6 的词。
   - 界面文案里不出现英文字母，§3.7 列出的词和 Key、ID、Token 除外。
   - 扫描 `app/`、推送和日报的界面字符串（注释和「详细原因」除外），命中禁用词就失败。
   - 扫描写在 `tests/ui-copy-guard.test.mjs`，范围随文案改动一批批扩大，改完的文件就加进去。
7. **新功能先对照本文。**本文没有的新概念，先在本文加一行，再写代码。

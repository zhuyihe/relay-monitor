# 界面用语规范

> 界面上出现的每一个字都按本文写：页面、按钮、提示、弹窗、表头、报错、导出文件、告警推送、日报。
> 本文是唯一来源。[ui-design-spec.md](./ui-design-spec.md) §6 只指向这里；代码里的文案表只放在 §12 列出的几处，并由测试守住。
> 起草和早期各批补充的日期，见[说法改动记录](./ui-copy-changes.md)开头。

## 1. 写给谁看

用的人是财务、运营、客服，不是写代码的人。他们懂收入、成本、利润、对账，但不知道系统内部怎么取数、怎么判定。

所以每一句话只需要回答三件事：

1. 这个数**能不能信**？
2. 要不要**我动手**？
3. 动手的话**点哪里**？

系统内部做了什么（重试、快照、版本、判定规则、接口、请求头）一律不说。

## 2. 七条原则

1. **先说对钱的影响，再说怎么办。**不说系统里发生了什么。
   - 对：「这把 Key 还给别处用吗？回答之前，利润先不算。」
   - 错：「消费范围待确认，金额仅供参考。」
2. **一个东西只有一个名字。**全站一致，包括按钮、提示、报错、推送和日报。名字见 §3。
3. **不出现后台用语。**英文代码、字段名、内部状态名、接口路径、HTTP 状态码和 §3.6 的词一律不上界面。数据里带着未知代码时，按 §5.5 显示，不把代码本身露出来。
4. **专业词只在要填写的地方出现。**例如站点地址、访问令牌、Webhook 地址，并且下面配一行白话说明（§3.7）。
5. **正常时不标。**「数据正常」「已核验」「有效」这类标签不显示，只在不正常时才说话。
6. **不确定就直说。**用「≈」「还在读取」「—」加一句原因，不用红色吓人，也不把估算当成准数。
7. **按钮用动词开头，同一个动作从头到尾一个名字。**按钮叫「重新读取」，完成提示就写「已重新读取」，弹窗标题也叫「重新读取」。

## 3. 词表

> 「（新）」「（旧）」两个标记（2026-10-25 起不只管 K）：
> - 「（新）」：已经定了，代码还没做；「（旧）」：已经定了要换掉，代码还在用。
> - 每一行随哪个 PR 做或换，只记在[待改总表](./pending.md)，规范的标记里不写 PR 名。
> - 做的那个 PR 里去掉「（新）」，或者删掉「（旧）」那一行，和代码一起合并。
>
> 例子：2026-10-25 用户定了算利润的新流程（[流程梳理稿](./ux/binding-flow.md)）：上游就是一个账号；渠道用哪把 Key 由「渠道 Key 读取服务」读出来，和上游的 Key 精确比对；界面上不出现「绑定」。§3.1、§3.5、§3.7、§5.2、§11 里很多「（新）」「（旧）」就是这次的：K1、K2、第一次使用改到哪一页，那一页就换成新的。

### 3.1 东西叫什么

| 用这个词 | 意思（可以直接用作界面上的说明文字） | 不再用 |
|---|---|---|
| 上游 | 你采购额度的地方；列表页叫「上游资源」，说某一个或几个时叫「上游」。新流程里一个上游就是上游网站上的一个账号（地址 + 令牌），下面有好几把 Key；同一个账号不再分开加成几个上游 | 站点、中转站、资源（单独用时）、监控站 |
| 上游账号 | 你在某个上游的登录账号。下拉里选上游时写「上游名 · 账号 42」，暂停监控的再加「 · 暂停监控」，不写类型名 | 账号身份、原始身份、稳定身份 |
| Key | 上游发给你的调用密钥，显示为 `sk-…abcd`。列表和下拉里写 Key 的名字；没有名字时写「Key #34」；同一个页面里两把 Key 同名时，两把的名字后面都加「（Key #34）」区分。一个页面里出现的 Key 放在一起比：上游账单比各账号下的 Key，渠道绑定比读到的 Key 和已有的绑定 | 令牌、实际 Key、canonical Key、sk 密钥 |
| 两把 Key 同名时（新） | K 以后 Key 都按打码写：前 4 位、后 4 位，不带 `sk-`，例如「AbC1…9f0c」（读取服务和上游的 Key 列表给的都是这样）。列表和下拉里照旧写名字；同一个页面里两把 Key 同名时，两把的名字后面都加打码区分：「oai（AbC1…9f0c）」。不再写「（Key #34）」：那个编号用户在上游后台里找不到 | Key #34（同名区分时）、sk-…abcd |
| 自营站点 | 你自己运营、卖给用户的站点 | 本站、我的站点、我的中转站、本站管理员站点、自营资源、自营业务站点、NewAPI 管理员站点 |
| 渠道 | 自营站点里的一条供货线路 | 销售渠道、本站渠道、上游渠道 |
| 绑定（旧） | 一把 Key 和自营站点里几个渠道的对应关系；有了绑定才能算利润 | 核算关联、关联、范围、来源绑定 |
| 看余额 / 算利润（旧） | 渠道绑定时对一个上游要做的两件事：「看余额」只读余额、发余额提醒；「算利润」绑定 Key，每天算利润。至少选一个，没选时写「请选「看余额」或「算利润」」，下面再写一句「「看余额」只读余额、发余额提醒，不用选 Key；「算利润」要选 Key，每天算利润」。只用 Key 的上游只能看余额 | 接入监控、对账、核算、监控与对账 |
| 在用 / 已解除绑定（旧） | 一条绑定现在还算不算利润；在「以前的每日记录」里选绑定时标在名字后面 | 生效中、已停用、已归档 |
| 没对上上游的渠道 | 渠道里填的地址找不到对应的上游。和「绑定」是两回事。新流程：渠道用的 Key 不在已加的上游里，每行写「这个渠道用的 Key 不在已加的上游里」[加上游]；渠道里填的地址对上了一个已加的上游、Key 却不在它的列表里的（新），写「这个渠道连的是「演示·主力账号」的网站，但用的 Key 不在这个账号里，可能是同一个网站上的另一个账号」[加上游] | 未关联上游资源的渠道、未直接关联监控站 |
| 在算利润 / 没算利润（新） | 一个渠道现在算不算利润。代替「绑定」「在用 / 已解除绑定」：界面上不说「绑定」，说「渠道」；汇总里写「其中 1 个渠道需处理，没算进来」，不写「1 条绑定」。例外：上游资源里渠道挂在哪个上游下面，用「绑定渠道」「解绑」（上游资源只管绑定、解绑，和利润没有关系；取代 #76 的「开始算利润 / 停止算利润」，见 §3.5） | 绑定、核算关联、在用、已解除绑定 |
| 用过的 Key（新） | 一个渠道在不同时间用过的 Key，连同分组和倍率，一段一行：「10月24日 14:30 起　oai-2 · 分组 a · 倍率 1.2」；已经结束的一段写「到 10月24日 14:30」。换的时刻定不出、两次读取之间隔得长的，写「15:19–16:05 之间换成 oai-2」（不写原因：是读不到那段时间、控制台重启还是别的，对算钱没有影响，用户不用做什么）（[流程梳理稿](./ux/binding-flow.md)第 3 节那条规则）。不写段号、token_id、指纹；Sub2API 上游读不到倍率，只写到分组；倍率暂时读不到时照 §5.4 写。写在「渠道」页签每个渠道下面 | Key 历史、Key 段、绑定记录 |
| 渠道 Key 读取服务（新） | 装在你站服务器上、和 New API 放在一起的只读小服务，读每个渠道填的 Key，只交出打码和指纹。第一次出现时写全名，同一处再出现简称「读取服务」 | 小服务、sidecar、Key 代理、渠道 Key 接口 |
| 渠道里用的其他地址（旧） | 渠道里填的不是上游的公开地址时（内网地址、代理地址），把那个地址填在上游里，才对得上 | 成本渠道匹配别名 |
| 分组 | 上游里的价格档位 | 分组目录 |
| 只走一个分组 / 失败自动换分组 | Key 的两种分组设置。只有「只走一个分组」的 Key 能绑定 | 固定分组、跨组重试 |
| 倍率 | 上游对一个分组收的价格倍数；细分时写「模型倍率」「分组倍率」「输出倍率」 | 路由、计价倍率、模型× |
| 用量记录 | 上游记下的每次调用和扣费 | 消费日志、账单证据、计量 |
| 记收费记录的那个开关（新） | 自营站点后台里管「记不记收费记录」的那一项。只在告诉用户去哪里打开时引用 New API 设置页上的原名，两套界面都写，新的在前：「系统设置 → 运维 → 日志维护 →「记录配额使用量」（旧版界面是：运营设置 → 日志设置 →「启用额度消费日志记录」）」。新界面 v1.0.0-rc.22 起只剩这一套；旧界面是 v0.8.0–v0.11.x，和 rc.21 以前选「经典」主题的（开发 10-25 照 New API 各版本的界面源码和中文翻译核过）。别处照「收费记录」说：「自营站点不记收费记录了」，不说消费日志 | 消费日志、记录消费日志、消费日志开关、LogConsumeEnabled |
| 收费记录 | 自营站点记下的向用户收费 | 渠道账单统计、本站收费流水 |
| 每日记录 | 每天定下来的那一行利润 | 结账记录、账本、快照、已确认账单 |
| 固定成本记录 | 固定成本的一笔：金额加天数 | 付费记录 |
| 登录信息 | 系统读取上游或自营站点用的访问令牌、登录令牌、用户 ID、密码、Key 的统称 | 凭证、凭据、连接凭证、授权、账号授权 |
| 超级管理员 | 自营站点里权限最高的账号（New API 里是 root，role 100）。设置自营站点时用普通管理员（role 10）的令牌也能连上、读得到渠道和收入，只是读不到自营站点的设置（§5.4） | root、管理员（root）、role 100、role ≥ 10 |
| 转售 Key | 用管理员账号开出来卖给客户的 Key，它的花费算收入 | 管理员转售 Key、管理转售 Key、转售的管理员 Key |
| 管理员自用 | 管理员自己在自营站点里用掉的额度，不算收入 | 管理员消耗、root 自用 |
| 历史数据 | 系统定时记下的余额和花费，不是每次调用的明细 | 监测历史、原始快照、监测快照、采集数据 |
| 通知方式 | 告警发到哪里：Telegram、钉钉、邮箱等 | 渠道、通知渠道、发送渠道（在告警中心里） |
| 官方渠道 | 自营站点里直连模型厂商、没有上游的渠道 | 官方 / 内置渠道（type N） |
| 已登录的设备 | 当前登录着这个控制台的浏览器 | 会话 |
| 软件版本 | 这套控制台的版本号 | 构建标识 |

没有名字的上游写「未命名上游」，没有名字的用户写「未命名用户」，不写「未命名资源」「（未命名）」。

### 3.2 钱叫什么

| 用这个词 | 怎么算 | 不再用 |
|---|---|---|
| 收入 | 自营站点向用户收的钱，来自收费记录。G 以后（新）：利润等式（运营总览、每日利润）里的收入只算在算利润的渠道，和每日利润同一个范围；自营业务第一行的「收入」是自营站点全部的收入，两者不一样时那一格下面写「其中 ¥18,420.50 算进了利润」；自营业务最后一格「毛利」下面写「9 个渠道算进利润（收入 ¥18,420.50）」，没有在算的渠道时写「还没有渠道在算利润」，整格去每日利润 | 本站收费、期内收入、销售额 |
| 上游成本 | 上游按用量扣的钱，来自用量记录。包月或按期付费的上游在这一格写「计入固定成本」，数字记 0 | 用量成本、消耗、消费、已计入上游成本 |
| 实付成本（已取消） | 每日利润表里也叫「上游成本」，不再单叫「实付成本」 | 实付、实扣、上游实扣 |
| 应付成本（新） | 自营站点这个渠道的用量，按上游的模型价格和这把 Key 的分组倍率算出来，上游应该扣多少。只给已经固定的整天算，只算 New API 上游；算不出时写「—」和原因（§5.7） | 预期成本、应收、按倍率应收、理论成本 |
| 固定成本 | 按月或按期付的钱（服务器、包月上游等），按天平摊 | 固定付费、固定采购、月费、摊销 |
| 毛利 | 收入 − 上游成本 | 利润（单独用时）、账面毛利、已确认毛利 |
| 净利 | 毛利 − 固定成本。固定成本算不出（有上游没设汇率）时写「固定成本算不出，净利先不算」，不写 0 | 净利润 |
| 毛利率 / 净利率 | 毛利 ÷ 收入 / 净利 ÷ 收入 | —— |
| 亏损 | 毛利或净利小于 0 时，数字旁的标签 | 负毛利 |
| 差额（新） | 上游成本 − 应付成本。正的写「多扣 $1.20」，负的写「少扣 $0.50」，后面跟「比应付多 15%」「比应付少 3.6%」。金额不上色 | 参考差额、风险差额、偏差、误差 |
| 对不上（新） | 差额同时超过 $0.05 和应付成本的 2% 时，差额后面的小标签；没超过的照常写数，叫「门槛以内」。只显示，不进需处理、不推送。门槛的两个数由代码里那一份给，页面不另写 | 异常、超差、不一致 |
| 比预期少赚 / 比预期多赚（新） | 一段时间里已经固定、算得出应付成本的那几行，差额加起来：正的写「比预期少赚 $0.71」，负的写「比预期多赚 $0.30」，都写正数。下面拆成「多扣 $1.20 · 少扣 $0.50 · 门槛以内 +$0.01」三项，加起来等于这个数 | 预期偏差、利润缺口 |
| 没算进利润的上游成本 | 上游账号实际扣的钱，减去已经算进利润的那几条绑定的部分（和汇总的上游成本同一个范围，§4）。需处理、还在读取的绑定，没有绑定的 Key、测试和自用，都落在这里。只在单天的范围（今天、昨天、选一天）显示：多天范围只现读还没固定的尾巴，读不到这一块的全貌，不显示。G 以后（新）：成本页「上游成本」那一格是上游账号实际扣的全部，下面拆开写「算进利润 ¥12,036.80 · 没算进利润 ¥104.60」，后一半点开列各上游；都算进去了只写第一格的数 | 未纳入核算的上游消费 |
| 算进利润 / 不算进利润 | 上游上的开关：这个上游的花费要不要算进利润 | 计入利润成本、不计利润成本、不计入利润 |
| 汇率 | 写成「1 美元 = 7.20 元」。没设置时的写法见 §7 | 换算比例、FX、1:1、$1 = ¥2、充值折算汇率 |
| 售价 | 给用户充 1 美元额度收多少元，写成「1 美元额度 = 7.50 元」，和汇率分开 | 售价汇率 |
| 预收 | 用户已经付了钱、还没用掉的余额 | 用户余额合计 |

没算进利润的上游成本算出来小于 0（已算进利润的比上游实际扣的还多）时，金额照实显示负数，旁边说明原因，只用这三句：

- 「已算进利润的多于上游扣费：上游的扣费可能还没记全」
- 「已算进利润的多于上游扣费：两边汇率不同」
- 「已算进利润的多于上游扣费：上游的扣费可能还没记全，两边汇率也不同」

「利润」只作统称，用在标题或句子里，例如「算利润」「利润暂时算不出」。具体的数字必须写明是毛利还是净利。

「消费」只用来说自营站点的用户花了多少（例如「消费最多的用户」），不用来说上游。

### 3.3 余额和提醒

这一组只用在看余额、提醒、可用天数的地方。

| 用这个词 | 意思 | 不再用 |
|---|---|---|
| 余额 | 上游账号里还剩的钱，按上游自己的币种显示（`$` 或 `¥`） | 站点余额、剩余额度 |
| 花费 | 余额减少了多少。只用在余额相关的地方：「今天花费」「日均花费」「花费时段」 | 消耗、消费、日均消耗 |
| 可用天数 | 余额 ÷ 日均花费，写成「可用约 3 天」。表格和「名称：值」里标签写「可用天数」，值写「约 3 天」。1 天以上四舍五入到整天；不到 1 天写「约 5 小时」，不到 1 小时写「不到 1 小时」；近期没有花费写「近期没有花费」（日均花费舍到分是 0、每天不到半分钱的也算，不给天数）；算不出写「—」 | 跑道、余额跑道、预计耗尽、4.6 天、无法计算 |
| 余额提醒线 | 余额低于这个数就提醒；单个上游可以另填。全局的在告警中心「余额偏低」那一行里设，写成「余额低于 5 时提醒」 | 阈值、告警阈值、低余额阈值、全局阈值 |
| 余额偏低 / 快用完 / 余额用完 | 余额只有这三档。「快用完」后面跟「可用约 N 天」（上游列表的表格里同一行已经有可用天数一格，状态格不再重复）。可用天数在提醒天数以内用红色，在 7 天以内也叫「快用完」、用黄色，不另起名字。还没读到写「还没读取」，读不到写「读不到余额」。上游列表状态格的下一行解释这一档（不写天数，天数在可用天数一格）：余额偏低「低于提醒线 $5」（提醒线按这个上游自己的币种，单个上游另填了的按它的）；快用完，红色时「按现在的花法，3 天以内就会用完」（3 天是提醒天数，按告警中心设的单位写，设成小时就写「48 小时以内」），黄色时「按现在的花法，7 天以内就会用完」；余额用完「充值以后才能接着用」 | 耗尽、已耗尽、即将耗尽、耗尽预警、7 天内耗尽 |

## 4. 每天只有三种状态

每条绑定的每一天，在界面上只会是下面三种之一。

| 状态 | 什么时候 | 怎么显示 |
|---|---|---|
| 实时 | 今天，数字还会变；或者过去某天系统还在自动重读（最多 7 天） | 「实时」，旁边写「数据截至 14:30」；过去的日子再加一句「还在读取」 |
| 已固定 | 过去的日子，数字定下来了，不会再变 | 「已固定」；鼠标悬停写「10月10日 0:05 固定」 |
| 需处理 | 不处理就算不准，需要有人动手 | 「需处理」，加一句原因和一个按钮，利润写「—」 |

判定顺序：

1. 有不处理就算不准的问题，就是**需处理**。
   - 只显示最要紧的一条，其余收起成「还有 2 个问题」。
   - 过去的日子超过 7 天还没固定、系统不再自动读的，也是需处理（§5.3「这天一直没固定」）（新）。
2. 否则，这天已经定下来了，就是**已固定**。
3. 否则就是**实时**，可以带一句提示，例如「还在读取」「从 10月9日 开始统计」「倍率在 14:30 变了」。

两条补充：

- **读不到账单这类问题**，系统会自己重读，所以先不算需处理：
  - 今天：显示为「实时」加提示。
  - 过去的日子：系统自动重读的 7 天里显示「实时」和「还在读取」；7 天后还没读到，才变成「需处理」。
- **有两种没有按钮的需处理（新）**：自营站点有一段没记收费记录的日子（§8.1、[流程梳理稿](./ux/binding-flow.md)附录 9，用户 10-25 定），和换 Key 冲突、分不清的日子（下面「这一天几个渠道换了 Key……」，总指挥 10-27 定）。这几天是需处理、利润写「—」、不固定、不算进汇总，但收入补不回来（换 Key 冲突那种是另一把 Key 的钱分不清该算给谁），没有能做的事，所以没有按钮，也不进需处理清单；原因写在那几天自己身上：「这一天自营站点有一段没记收费记录，那段的收入补不回来」「这一天几个渠道换了 Key，分不清哪把 Key 的钱该算给哪个渠道，这天没算」。只有这两种例外，别的需处理照上面都有一句原因和一个按钮。
- **不影响结果的事不改变状态**，只在对应位置加一个小标签或一句提示：
  - 渠道停用，在渠道名旁标「已停用」。
  - 倍率变了，加一句提示。
  - 统计开始时间，写「从 X 开始统计」。
  - 每日利润重做以后（新）：开始算利润那天从 0 点算起，点以前今天已经产生的用量也算（两边记录读得到就行，用户 10-26 定）。「从 X 开始统计」都改成只写日期的「10月24日 开始算」，今天开始的写「今天 14:30 开始算，0 点以后的都算进来了」；「还没开始统计」改成「还没开始算」，§8.1 那句写「这天还没开始算。最早的渠道从 10月24日 开始算。」；Sub2API 上游那天「从 0:00 开始统计（这个上游只能按整天读账单）」那一句也不再要（[A 细化稿](./ux/daily-profit-a.md)第 7 节）。

其他标签只允许这几个：

- 「改过」：已固定的日子后来被重算过。
- 「亏损」
- 「已停用」「已删除」：只用在渠道上；「已停用」也用在「用过的 Key」里上游那边停了、删了的 Key 上（新）。
- 「≈」：估算。

整天在开始统计之前的日子不算三种状态里的任何一种，只写灰字「还没开始统计」（§5.4）。

汇总怎么加（每日利润的汇总和每组小计，一段时间、多天合计都一样）：

- 收入、上游成本、毛利只加算出来的绑定（毛利已经算出来、又不是需处理），三个数用同一个范围，财务一减就对得上（收入 − 上游成本 = 毛利）。
- 需处理的、还在读取（毛利还没算出来）的都不加，金额留在绑定列表它自己那一行；汇总旁边写一句没算进来什么（F2）：
  - 只有需处理的：「其中 1 条绑定需处理，没算进来」；
  - 只有还在读取的：「其中 2 条绑定还在读取，没算进来」；
  - 两种都有：「其中 1 条绑定需处理、2 条还在读取，没算进来」；
  - 这段时间只有一天时点名日期，例如「其中 10月22日 有 1 条绑定需处理，没算进来」；
  - 按天（多天合计）：「其中 2 天需处理，没算进来」。
  - 已固定、又因为重算的事（少了一半多、太早、没重算成）需处理的，照算进汇总，旁边另写一句（有「没算进来」那句时分成两句，这句在后）：只有一天「其中 10月8日 有 1 条绑定还没重算，先按原来固定的数算。」；多天「其中 1 条绑定有 3 天还没重算，先按原来固定的数算。」（多天的随 E）（几条绑定时「其中 2 条绑定有几天还没重算，先按原来固定的数算。」）。三种原因对用户是同一件事，这里不分开说，具体原因在那一行的需处理里；「先」字表示以后会变。
  - 每日利润按渠道一行以后（新）：「其中 2 个渠道需处理、1 个还在读取，没算进来」。每日利润重做以后（新）这一句不写，换成顶上「没算进来 1 个渠道」一格和表的合计行「合计（算进来的 6 个渠道）」，数法不变（[A 细化稿](./ux/daily-profit-a.md)第 2 节）。数的是渠道，不是行数：同一把 Key 的几个渠道并成一行（「高速 A、高速 B（同一把 Key）」），这一行需处理就算 2 个。
  - 已固定、又因为重算的事需处理、照算进汇总的那几行，在合计行的括号里写「其中 1 个还没重算，先按原来固定的数算」（数渠道；手机写在顶上那张卡片的最后一行，不带「合计」）；第 308 行那句随每日利润重做不再单独写。有几天还没重算的天数，等逐天的数据（随 #125）再接上。

G 以后（新）：运营总览的利润等式和每日利润的汇总是同一份数（[G 等式只放两处](./ux/g-equation.md)），等式下面那句没算进来的也照上面写，后面接「另有 ¥104.60 上游成本没算进利润。」[查看各上游]；原来等式下面那一长段「数据不完整，带 ≈ 的数字是……」和一串没设置汇率的上游名不再写。

多天合计的写法：

- 都定下来了：「7 天已固定」。
- 混合：「6 天已固定，今天实时」。
- 有需处理的日子：照常显示其余日子的合计，旁边写上面那句。

改设置时，保存前提示一句：「今天按新设置重算；以前还没固定的日子先按原设置固定，不受影响。」如果有的日子没能固定，保存后提示「有 2 天没能固定，已放进需处理」。

## 5. 问题怎么说

### 5.1 一条问题的写法

```
[需处理]  标题：一句话说发生了什么（用户的话）
          说明：对利润的影响 + 怎么办（可省略）
          [按钮]                还有 2 个问题 ▾
```

- 标题不超过 20 个字，不带句号。
- 说明一句话。原因已经能看懂时，说明可以省略。
- 只放一个按钮，名字来自 §3.5。
- 同一条绑定有多个问题时，只露出最要紧的一条，其余收起。
- 附注（新，需处理清单里一条事的第三行，最多一行）按这个先后取一种：带日期的事写日期（§6「一条事附注里的日期」）；渠道上不处理就不算利润的事，知道从哪天起时写「10月20日起没算进利润」；上游、自营站点的事挡住了几个渠道时写「3 个渠道的利润在等它」；同一个对象还有别的问题时写「还有 1 个问题：……」。
- 需处理清单（新）：一件事 = 一个对象 + 一个问题 + 一个按钮；对象是上游、渠道、Key、自营站点之一，名字写在标题前面，标题里已经点了对象名的不再写（[E 设计稿](./ux/e-attention.md)第 2、3 节）。同一个对象只占一行；同一个原因只说一次。
- 「还有 N 个问题」和「还有 N 件」不是一回事，两个说法都留着：「还有 N 个问题」是一个对象（一条绑定、一个上游）身上还有几个问题；「还有 N 件」是需处理清单只露了前几条，下面还有几件事（运营总览，ui-design-spec §5.1）。

- 已经有余额档位（例如「余额偏低」）时，状态格写「余额偏低 · 还有 1 个问题」（数的是事的件数，档位本身不算），下一行写这一档的说明（§3.3），不写事的标题，免得读起来像在解释档位；事的按钮照样在行末，鼠标悬停、键盘聚焦时提示「测试读取：还没确认…」（按钮名：标题），读屏念同一句；没有档位的行，标题已经写在状态格里，按钮上不再说一遍，其余几件在「⋯」最上面。余额档位本身也是需处理的一种（E 设计稿第 2.2 节的余额类），所以页顶筛选「需处理」也数这些行。（版式 PR 5 改）

### 5.5 删除和兜底

**删除。**下面这些码现在不会再产生，界面文案一并删除：

- STALE
- GROUP_OR_RATIO_CHANGED
- BILLING_WINDOW_UNCONFIRMED
- OWN_FLOW_INCOMPLETE

以前的数据里如果还带着这些码，统一显示为「这天的数据不完整」，归读取类处理。

**删上游时（新）。**删除上游的确认框里多写一句「这个上游下 3 个渠道也会停止算利润」（个数按渠道数），确认删除时这几个渠道一起停止算利润；已经算出来的日子留着，上游加回来以后可以再点「开始算利润」。所以「上游已经删了」那条需处理（§5.2）只给不是从控制台删掉的情况。

**名字找不到时。**上游已经删掉的写「已删除的上游」，提示里要点名时写「已删除的上游（编号）」；Key 和渠道没有名字时按 §3.1 写「Key #34」「渠道 #12」。

**兜底。**遇到表里没有的码时：

- 显示「需处理：这条暂时算不出利润」和「刷新」按钮。
- 码本身只写进浏览器控制台，界面、推送和日报上都不显示。

| 「—」 | 这一行需处理，原因写在这一行下面（§5.2） |

- 不写 0：今天、算不出的都不写「$0.00」。
- 范围里有还没固定的日子时（今天、近 7 天、本月），差额只加已经固定的那几天，表头写「差额 已固定的 6 天（10月20日–10月25日）」，不连着时只写「已固定的 6 天」，后面写「其中 2 天对不上」。

## 6. 时间

| 场景 | 写法 |
|---|---|
| 数据时间 | 当天写「数据截至 14:30」；不是当天写「数据截至 10月9日 14:30」 |
| 一行的数据旧了（上游列表） | 只在比服务端此刻旧「2 × 刷新间隔 + 30 秒」以上的那一行写「数据截至 14:20」（规则同上），前面一个小钟；悬停和读屏还有一句「后面几次刷新都没读到这个上游的新数据」。新的行不写，表格里也不再有「数据截至」一列；所有上游都旧了时每一行都写 |
| 日期 | 今年写「10月9日」，往年写「2025年10月9日」 |
| 一整天 | 只写日期「10月9日」，不写「00:00 – 次日 00:00」 |
| 日期范围 | 「10月1日–10月7日」，同月也写全两个日期 |
| 时刻 | 24 小时制「14:30」，不写秒 |
| 时段 | 「21:00–22:00」，和日期范围一样用短横线 |
| 一条事附注里的日期（新） | 连着的三天以上写「10月14日–10月16日」；只有两天写「10月14日、10月15日」；不连着的最多写三天「10月9日、10月11日、10月14日」；再多写「10月9日 等 5 天」 |
| 格子、小格里的日期（新） | 表头或上面一句已经写了月份时，一格只写「20日」；今天那一格写「今天」（每日利润点开一行的每天差额） |
| 星期 | 「周一」到「周日」 |
| 时间范围 | 「今天」「近 7 天」「近 30 天」「近 90 天」；按小时看的写「近 24 小时」（用量分析、余额趋势），余额趋势另有「近 3 天」；自己选的写「10月1日–今天」。同一个范围全站一个名字，不写「今日」。每日利润另有「开始算以来」，放在「本月」后面、「自定义」前面：从最早开始算的那个渠道那天到现在，每个渠道从它自己开始算的那天起算；页顶一句写「10月20日–今天 · 开始算以来」 |
| 时区 | 一律按业务时区显示，包括推送、日报和日报发送时间。只有和业务时区不同时才写，例如「按 UTC 时间算一天」 |
| 一天 | 业务时区的 0:00 到 24:00；界面上不解释，只在设置页说明一次 |

界面上禁止出现 ISO 格式（`2026-10-09T06:30:00.000Z`）、`YYYY-MM-DD`、时间戳数字、时区代码（`Asia/Shanghai`），以及「窗口」这个词。

## 7. 数字和金额

设计规范 §4.5 的币种、精度两行，以下面为准：

- 金额按系统里的原始币种显示（美元写 `$214.30`）。只有设置了汇率才换算成人民币，换算处标「按 1 美元 = 7.20 元换算」。
- 「每日利润」页没设置汇率时不折算，写「没设置汇率，按美元显示」。
- 运营总览、上游资源、成本估算、用量分析、自营业务这几页目前没设置汇率时仍按 1 比 1 折算，文案照实写「没设置汇率，暂按 1 美元 = 1 元算」。要不要改成不折算，另外决定，不在本次范围。
- 自营站点那一格叫「售价」（§3.2），写成「1 美元额度 = 7.50 元」；没设置时写「没设置售价，暂按 1 美元额度 = 1 元算」。上游照旧叫汇率。
  - 上游编辑页打开「这是我的自营站点」后，「汇率」那一格改叫「售价」。
  - 说明写「例如填 7.5 就是「1 美元额度 = 7.50 元」；不填就是「没设置售价，暂按 1 美元额度 = 1 元算」。」，填了以后写「1 美元额度 = 7.50 元。」，不写「余额提醒照上游自己的余额算」。
- 余额按上游自己的币种显示，推送里也一样，不一律写 `$`。

另外几条：

- 不知道的数写「—」，旁边或悬停写原因。不写 0、不写空白、不写 NaN。
- 毛利率 = 毛利 ÷ 收入，写一位小数「38.1%」；收入不大于 0 时写「—」。每日利润表有「毛利率」一列，合计行也写。
- 估算值前加「≈」，后面跟一句为什么是估算。
- 每日利润按人民币显示时，固定成本和没算进利润的上游成本是按自营站点的汇率换的，数前带「≈」（「扣固定成本 ≈ ¥60.58 后，净利 ≈ ¥1,010.82」「另有 ≈ ¥30.24 上游成本没算进利润」）；计算明细里应付成本那张表按美元原币，整页按人民币时表上面一句灰字「这张表按美元原价」。
- 亏损的数字仍用墨色，前面用真正的减号「−」，旁边标「亏损」。
- 笔数写「3 笔在用，1 笔还没开始，1 笔已到期」，只写不为 0 的，不写「生效 3/4 笔」。全部到期写「已到期」；只有一笔、在时间范围中途才开始或还没开始时写「10月12日起」（日期按 §6），从范围开始前就在用的不写。
- 上游列表里固定成本上游的状态：在用的不标，下面写笔数句或「最近一笔 10月30日到期」；提醒天数以内有一笔到期写「3 天后到期」；全部到期写「已到期」，下面写「要续上，再记一笔固定成本」；都还没开始写「还没开始」；一笔都没记写「还没有固定成本记录」。可用天数一格写「还剩 3 天」，没有到期日写「—」。
- Token 数、请求数大时用「万」「亿」：「1.2 万」「3.4 亿」，不写 K、M、B。
- 占用空间写「2.0 KB」「1.5 MB」「3.20 GB」，单位照写，不算多余的英文。
- 很小的金额最多写到 8 位小数；小到 8 位小数也是 0 的，按三位有效数字写成小数（`$0.00000000123`），不写成 0，也不写科学计数 `1e-9`。
- 单价（每百万 Token 价格）最多 4 位小数。

归类的顺序（开发用）：先看错误码，再看是不是 §5 的问题码，再看原文里的关键词，再看 HTTP 状态，都不是就算「其他」。错误码到类别的对照只在 `lib/error-copy.js` 里维护，这里不重复列。原文里的数字（429、500、404 这些）不当关键词认：读上游时在出错的地方按上游的状态给码，我们自己接口的状态按 HTTP 状态归类。

「详细原因」的规则：

- 默认收起，链接写「查看详细原因」，展开后是原文和一个「复制」按钮，标题写「发给技术同事看」。

- 原文里的密钥、令牌照旧打码。
- 通知方式没连上对方时，fetch 的原文只有「fetch failed」，后面补上底层原因（拒绝连接、域名找不到、证书不对），同样打码（`lib/error-copy.js` 的 `errorDetail`）。

### 8.3 告警中心、系统设置：改了马上保存

这两页的设置都是改了马上保存，不放「保存」按钮（修改密码除外，它要原密码，照旧按「修改密码」）。

| 情况 | 写法 |
|---|---|
| 区块标题旁，保存中 | 「保存中…」 |
| 区块标题旁，保存好了 | 「已保存 14:30」 |
| 数字框什么时候存 | 离开输入框或按回车时；没改就不存 |
| 开关、下拉、勾选什么时候存 | 一改就存 |
| 存不进去 | 区块标题旁写哪一组没存上：「余额提醒线没存上：原因。」（原因照 §8.2，后面跟「查看详细原因」）。这一组再提交一次（改回原值，或者改成别的值存成功）就清掉。输入框回到最新已保存的值（还在改的不动）。组名：提醒规则、余额提醒线、提醒开关、日报设置、自动刷新间隔、历史数据保留 |
| 缩短保留天数时预览读不到 | 同上：「历史数据保留没存上：原因。」，回到原来的天数 |
| 等用户回答确认框时 | 不写「保存中…」 |
| 几组接连改 | 一组一组按顺序存，后面的排着，不丢；同一组排着好几次时只存最后一次（旧值不存、也不为旧值弹确认框）；同一组同一个值还没存完，不再发一次 |
| 缩短历史数据保留天数 | 选了以后先弹确认框（照旧）；取消就回到原来的天数 |
| 区块说明 | 告警中心「提醒规则」写「改了马上保存。……」（现有）；系统设置每块不再写保存的事 |

**告警中心还没有通知方式时**，整页只放这一件事，加一小块两个数：

- 标题「还没有通知方式」；
- 说明「先加一个通知方式，提醒和日报才发得出去。加好以后，打开的提醒都会发到这里，提醒规则和日报在这一页再调。可以选这些：」（不列规则名：关掉的规则不会发）；
- 下面是各种通知方式的按钮，再一个「添加通知方式」。
- 提醒规则、日报这时不显示；页顶那条「还没有通知方式，提醒发不出去」也不再单独出（说的是同一件事）。
- 下面另放一小块「余额提醒线和提醒天数」，只有这两个数，说明「这两个数决定运营总览、上游列表、成本估算里标不标「余额偏低」「快用完」；加了通知方式以后，也按它们提醒。」提醒线下面只写前半句「按各上游自己的余额单位比，不换算；单个上游可以在编辑上游里另填。」（后半句和说明重复）。余额提醒线读不到时，这一块里就地写「读不到余额提醒线：原因。」[刷新]。有了通知方式，这两个数只在提醒规则那几行里，不两处同时出现。
- 为什么多放这一小块：这两个数是系统自动标档位用的，用户要能更正（§1.2 第 2 条）；只放通知方式的话，还没加通知方式的人就没处改了。

**「余额偏低」那一行**（提醒规则表里）：

- 条件写「余额低于 [5] 时提醒」，数字框和「快用完」那一行的天数框一样。
- 下面一句「按各上游自己的余额单位比，不换算；单个上游可以在编辑上游里另填。这条线也决定页面上标不标「余额偏低」，关掉提醒也照样标。」规则名下不再写「余额低于余额提醒线时通知」（和这一行重复）。
- 「快用完」那一行的提醒天数同样：关掉提醒也能改（它也决定页面上标不标「快用完」）。只有「读不到余额」的「连续读不到几次」在关掉时禁用。
- 没填时报「请填余额提醒线；不需要余额偏低的提醒可以填 0」（现有），小于 0 报「余额提醒线不能小于 0」（现有）。
- 币种怎么标，G 再定（G 清单 3.2），这次不改。

**系统设置**原来的「余额提醒线」区块拿掉，「刷新与数据」下面加一句「余额提醒线在告警中心里设。」，「告警中心」是链接。

**系统设置「刷新与数据」里的「算应付成本」开关（新，应付成本 V1-b）**：

- 名字「算应付成本」，开关，默认开；改了马上保存（本节上面的规矩）。
- 下面一句说明：「开着时，系统定时读自营站点的收费记录（只读，不改自营站点的任何东西），按上游的价格和倍率算每天的应付成本，和上游实付的对一对。关了就不再读，每日利润里的应付成本和差额写「—」，收入、上游成本、毛利照常；关着那几天固定的，以后打开也不补算。」
- 开着时再下面一行灰字写读到哪儿了：「收费记录读到 10月26日 14:30」；落后 1 小时以上时写「收费记录只读到 10月25日 14:30，自营站点的记录多，系统在接着读」。关着时不写这一行。

**日报**：开关、发送时间、发到哪里改了就存；「立即发送」旁那句「「立即发送」按已保存的设置发」不再需要，删掉。

## 10. 推送和日报

推送和日报用和页面一样的词，在发送的代码里直接写成最终文字，不再发送前用替换改写。

**只推余额提醒（新）**；什么时候推的规则和以前一样，只有这几处不同：

- 余额已经用完时不再推「快用完」（原来余额用完后还会补推一条「快用完，可用不到 1 小时」，透支的上游会一直推）。所以关掉「余额用完」这条提醒时，余额用完后就没有提醒了。
- 「快用完」和页面一样，最近在花钱才提醒：近期没有花费时不推（原来只看估算的可用天数：余额只剩几分钱、每天花不到半分钱时，估算把日均花费舍成 0、天数却照算，会推一条正文写「近期没有花费」的快用完）。
- 读余额暂时失败、还没到「连续读不到几次」时，不发「持续告警」（不拿旧的余额档位再提醒一遍）。
- 上游自己的余额提醒线没填时用全局的，包括旧数据里存成空的（和页面一样）。

**每日利润的需处理不单独推送，写进日报的一行里（新）**（见下面「日报」）。

**重复提醒**：同一种情况（余额一直在那一档）一直没好，每隔「重复提醒间隔」再发一次，从上一次发出时起算，不管送没送到。

**没送到时**（通知方式回了错误、连不上）：

- **一件事**：同一种提醒说的同一种情况。余额偏低、余额用完、读不到余额、恢复正常、快用完、不再续费的单次提醒各算一种。情况一直在，或者离开不到 24 小时又回来，都算同一件事；离开满 24 小时再出现，才是新的一件事。
  - 离开：那种情况不在了——余额不在那一档了、关掉了这种提醒、不再算快用完（包括估不出来、改了提醒天数）、改了「不再续费」。读不到余额的那段时间也算离开（除了「读不到余额」这件事本身），这段时间不补；读不到满 24 小时，读回来还在原来那一档，也是新的一件事。离开以后又停机、暂停监控，这段时间也算在离开里；停机前后一直在的，还是同一件事。
  - 「读不到余额」本身没到「连续读不到几次」时，不算离开也不算在。
  - 恢复正常：上游一直正常，也算这件事还在。所以之后不到 24 小时就解决的问题，恢复通知只发一次，没送到不补。
- 一件事第一次发出的那一条（不管是第一次提醒还是持续告警）没送到才补：间隔 1、2、4…分钟，最长 1 小时一次，从第一次发出起最多补 24 小时；中间离开的那段时间不补，也照样算在 24 小时里。
- 同一件事之后再发的（重复提醒、回到这一档时的那条）每次只发一次，没送到也不另外补；收到了的，不再补第一条。所以一个通知方式一直坏着时，第一天补满，之后每天只跟着重复提醒试。
- 只补给这种提醒现在还会发给它、第一次就要发但还没收到的通知方式：改了配置的照样补；后来加的不补；停用的、从这种提醒里去掉的直接划掉，再启用也不补。
- 几种提醒各补各的，一种补不出去不耽误别的，几种一起到点时同时发。
- 没有可用的通知方式时不攒提醒，加上通知方式以后也不补发之前的。

**令牌坏了的推送（过渡期，随 E 去掉）**

- **什么时候推**：一个上游、或者自营站点的令牌坏了（访问令牌作废、令牌少了权限），按站点只推一条，不管下面有几个渠道在算。重复提醒、没送到时补发，照上面现有的规矩（一件事 = 这个站点的令牌坏了）。换好令牌以后不推恢复：换令牌是用户自己做的，做完页面上那一条就没了。
- **标题**（也在下面标题那张表里）：「【炬元告警】Foo 访问令牌已经作废了」「【炬元告警】自营站点 My Site 访问令牌已经作废了」（站点没起名字时写「【炬元告警】自营站点 访问令牌已经作废了」）；少了权限的主语同上，后面写「令牌少了权限」，标题里不写少的是哪一项，那一项写在正文里。上游没起名字时写「未命名上游」。
- **正文**每行「名称：内容」：「上游：Foo」，自营站点写「自营站点：My Site」（站点没起名字时不写这一行：标题里已经写了「自营站点」，只有一个自营站点）；「状态：访问令牌已经作废了」或「状态：令牌少了「channel:read」的权限」（不知道少的是哪一项时写「状态：令牌少了权限」）；「影响：这个上游下 3 个渠道的利润先不算」（自营站点写「影响：各渠道的利润先不算」，数的是渠道，同一把 Key 的几个渠道算几个，和 §4「其中 2 个渠道需处理」同一个数法）；说明和 §5.2 用同一份句子，权限清单也是同一份：作废写「说明：New API 升级以后旧式的访问令牌不能用了，要换一个新令牌（nap_ 开头），并勾上这些权限：profile:read、api_key:read、usage:read」；少了权限、知道是哪一项写「说明：给令牌补上这项权限，或者换一个带这项权限的令牌」；不知道是哪一项写「说明：New API 没说少的是哪一项。给令牌勾上这些权限：……，或者换一个带这些权限的令牌」；再是「时间：10月9日 14:30」和落款「炬元告警中心」。

例：

```
【炬元告警】Foo 访问令牌已经作废了
上游：Foo
状态：访问令牌已经作废了
影响：这个上游下 3 个渠道的利润先不算
说明：New API 升级以后旧式的访问令牌不能用了，要换一个新令牌（nap_ 开头），并勾上这些权限：profile:read、api_key:read、usage:read
时间：10月9日 14:30
炬元告警中心
```

**自营站点的设置一直读不到的推送（R2）**：格式同上一条。一天多读不到自营站点的设置（5xx、超时、限流；收费记录本身读得到），按自营站点只推一条；读通了不推恢复。

```
【炬元告警】自营站点 My Site 设置一直读不到
自营站点：My Site
状态：设置一直读不到
影响：看不出它还记不记收费记录；利润照常算，要是这段时间里收费记录关过，那段的收入会算少
说明：自营站点恢复以后会自己好；也可以在运营总览的需处理里点「重新检查」
时间：10月26日 14:30
炬元告警中心
```

站点没起名字时标题写「【炬元告警】自营站点 设置一直读不到」，正文不写「自营站点：」那一行。

**标题**

| 什么时候 | 标题 |
|---|---|
| 余额偏低 / 余额用完 / 读不到余额 | 【炬元告警】上游名 余额偏低 |
| 令牌作废（上游、自营站点；过渡期） | 【炬元告警】Foo 访问令牌已经作废了 / 【炬元告警】自营站点 My Site 访问令牌已经作废了 |
| 令牌少了权限（同上） | 【炬元告警】Foo 令牌少了权限 / 【炬元告警】自营站点 My Site 令牌少了权限 |
| 自营站点的设置一直读不到（R2） | 【炬元告警】自营站点 My Site 设置一直读不到 |
| 快用完 | 【快用完】上游名 可用约 3 天（天数和正文的「可用天数」是同一个；算不出时只写上游名） |
| 持续没处理 | 【持续告警】上游名 仍是「余额偏低」 |
| 恢复 | 【恢复通知】上游名 已恢复正常 |

不再续费的上游第一次余额偏低（或者一下子用完）时只提醒这一次，标题照第一行写（「余额偏低」或「余额用完」）。没起名字的上游写「未命名上游」。

**正文**每行写「名称：内容」，只用下面这些名称：上游、自营站点（令牌坏了的推送里用）、状态、余额、日均花费、可用天数、影响（令牌坏了的推送里用）、原因、说明、时间。最后一行是落款「炬元告警中心」，不写名称（钉钉、飞书机器人的关键词靠它，见下面「关键词」；太长要截时也不截它）。

- 状态：写档位名「余额偏低」「余额用完」「读不到余额」「快用完」；恢复通知不写这一行。
- 余额：设了汇率写「$12.30（约 ¥88.56）」，没设写「¥12.30（没设置汇率）」，和上游列表手机版那一行一样。
- 日均花费：按汇率折成人民币（没设置汇率按 1 比 1，和上游列表一样），前面加「≈」：「≈ ¥15.12」；近期没有花费时不写。
- 可用天数：「约 3 天」，近期没有花费写「近期没有花费」。
- 余额用完、读不到余额时不写日均花费和可用天数。
- 原因：读不到余额时写 §8.2 那一类的话，例如「原因：登录信息不对或过期了」，不写上游返回的原文。
- 说明：只在不再续费的上游那一次提醒里写「说明：这个上游不再续费，只提醒这一次」，这个上游别的推送不写。
- 时间：按业务时区，「10月9日 14:30」。补发时写补发的时间，余额、日均花费也是补发那一刻的；不再续费的那一次提醒，标题和状态也写补发那一刻的档位（偏低或用完）。

例：

```
【炬元告警】Foo 余额偏低
上游：Foo
状态：余额偏低
余额：$4.00（约 ¥28.80）
日均花费：≈ ¥15.12
可用天数：约 2 天
时间：10月9日 14:30
炬元告警中心
```

**测试消息**（告警中心里点「测试」「发送测试」）：

- 标题「【测试通知】炬元告警中心」。
- 正文四行：「这是一条来自炬元控制台的测试消息。」「通知方式：运维群」「时间：10月9日 14:30」，最后一行和推送一样是落款「炬元告警中心」（测试能过，真推送也能过）。
  - 「通知方式」写填的名字；还没起名字时写类型名，例如「钉钉群机器人」，不写 dingtalk 这类代码。存库时没起名字的会存成「未命名通知方式」，也按没起名字写类型名。

**关键词**：钉钉、飞书的群机器人常设「自定义关键词」，消息里没有这个词就拒收。推荐的关键词是「炬元」（§8.2），所以每条推送、测试消息和日报都要带这两个字：告警中心落款「炬元告警中心」、测试消息标题「【测试通知】炬元告警中心」、日报标题「【炬元日报】」和落款「由炬元控制台生成」。新加一种消息时也要带上。

**太长时**：聊天软件一条消息有长度上限，超出的部分截掉，末尾写「……（太长没发完，完整内容请看邮件或控制台）」；推送和测试消息的落款仍在最后一行，在这句后面。按下面的数截（`lib/notify.js` 的 `LIMITS`）：企业微信 2048 字节（上限就是 2048，标题也算在里面）；Bark 3000 字节（走苹果推送，整条约 4KB，给别的字段留了余量，标题也算）；ntfy 4000 字节（上限 4096，留了余量）；其余聊天软件 1500 字；邮件 20000 字，放得下整份日报。

**日报**

标题「【炬元日报】My Site 10月15日」，自营站点没起名字时写「自营站点」。文字版（聊天软件收到的）按这个顺序写，每块前面写「■ 块名」：

```
【炬元日报】My Site · 10月15日（周四）
统计的是 10月15日 一整天

■ 经营概览
消费：¥1,234.00（环比 +12.3%；比前 7 天日均 ¥1,100.00 高 12.2%）
收入：¥1,000.00 ｜ 管理员自用：¥234.00
上游成本：¥600.00 ｜ 毛利：¥400.00（毛利率 40.0%）
固定成本：¥100.00 ｜ 净利：¥300.00（净利率 30.0%）
利润怎么算：2 个在用的渠道没对上上游；已添加的上游照常算成本。

■ 用量
请求数 1.2 万 ｜ Token（不含缓存）80 万 ｜ 有消费的用户 23 个

■ 用得最多的模型
1. gpt-4o  ¥340.00（Token 80 万 · 请求数 3,000）

■ 消费最多的用户
1. alice（管理员）  ¥34.00（Token 5 万）

■ 成本明细
- Foo  ¥600.00（按用量算）
- 服务器  ¥100.00（固定成本）

■ 上游余额
- Foo：$400.00（约 ¥2,880.00），快用完，日均花费 ≈ ¥600.00，可用约 5 天
- Bar：$4.00（约 ¥28.80），余额偏低，日均花费 ≈ ¥15.12，可用约 2 天
- Baz：读不到余额（登录信息不对或过期了）

■ 预收：¥5,000.00（120 个用户）

■ 预计花费
今天：预计 ¥1,100.00 到 ¥1,400.00
未来 7 天：预计 ¥7,000.00 到 ¥9,000.00
按过去 34 天估算，过去 2 周平均差 ±8%

由炬元控制台生成
```

- **日期**按 §6：往年带年份，星期写「周四」。统计的那天写在开头两行，落款那行只写「由炬元控制台生成」。
- **金额**按 §7 写，自营站点的金额按售价折成人民币（没设置售价按 1 比 1 算，「利润怎么算」里有那句）。估算的数和页面一样前面加「≈」：没设置售价时的收入；有按余额变化估算的上游、或上游没设置汇率时的上游成本；有这几种情况时，毛利、净利和两个利润率也加。
- **消费**：自营站点所有用户这天的消费，含管理员自用。括号里两个对比，用「；」隔开，各自算不出就不写，都不写时不带括号：
  - 环比：和前一天比；前一天没有消费时不写。
  - 前 7 天日均：这天之前 7 个整天（不含这天）每天消费的平均；前面不满 7 天，或者平均是 0 时不写。差多少写「高 12.2%」「低 5.0%」，四舍五入后是 0.0% 时写「和前 7 天日均持平」。
- **毛利、净利**：亏损时写「−¥30.00（亏损）」，不写利润率；收入是 0 时也不写利润率。
- **利润怎么算**：利润的几条说明，影响准不准的（估算、没设置汇率或售价）在前，其余在后，每条带句号；一条都没有时不写这一行。
- **读不到的**写「没读到（原因）」，原因是 §8.2 那一类的话；原因相同的几项合成一行：
  - 收入确认不了（用户身份或转售记录没读全）：「收入、管理员自用、毛利、净利：没读到（用户身份或转售记录没读全）」，下一行照常写「上游成本：¥600.00 ｜ 固定成本：¥100.00」；「利润怎么算」照写，只关乎收入的那条（没设置售价）不写。
  - 成本读不到（读不到自营站点的渠道列表）：收入那一行照写，下一行写「上游成本、固定成本、毛利、净利：没读到（原因）」，原因按 §8.2，多半是「自营站点暂时读不到，请稍后再试」；「利润怎么算」「成本明细」不写。
  - 两样都读不到：「收入、管理员自用、毛利、净利：没读到（用户身份或转售记录没读全）」，下一行「上游成本、固定成本：没读到（原因）」。
- **用量**：请求数、Token 大时写「万」「亿」（§7）；有消费的用户是这天消费金额大于 0 的用户个数（只调了免费模型的不算）。
- **用得最多的模型**、**消费最多的用户**：按消费各列前 5 个（用户只列消费金额大于 0 的），这天没有消费写「（这天没有消费）」。管理员后面写「（管理员）」；用户列表读不到时，下面写「（用户身份没读到，管理员没标出）」。
- **成本明细**：每个算进利润的上游一行，括号里写成本是怎么来的：有说明的写说明（「读不到用量，改按余额变化估算」「2 笔在用，1 笔已到期」），没有的写来源名「按用量算」「按余额变化估算」「固定成本」（§3.3）。按余额变化估算的金额前加「≈」。
- **上游余额**：在监控的上游，不含自营站点、固定成本上游和归档的。一个上游一行：
  - 余额和推送的写法一样：「$4.00（约 ¥28.80）」，没设置汇率写「¥4.00（没设置汇率）」。
  - 后面写档位名（余额用完、余额偏低、快用完；正常不写），再写「日均花费 ≈ ¥15.12，可用约 2 天」；近期没有花费只写「近期没有花费」；估不出来就不写；余额用完时不写日均花费和可用天数。快用完和页面同一套分档（§3.3）：按提醒规则里的提醒天数和 7 天线，不再写死 3 天，也不标 ⚠。
  - 还没读到写「还没读取」；读不到写「读不到余额（登录信息不对或过期了）」，原因按 §8.2，不写上游返回的原文。
  - 一个上游都没有时写「（还没有上游）」。
- **预收**：「预收：¥5,000.00（120 个用户）」，不算管理员；用户列表读不到时写「预收：没读到（用户身份或转售记录没读全）」。
- **预计花费**：有 3 天以上的消费记录才写这一块。「今天」「未来 7 天」写以往起伏范围「预计 ¥a 到 ¥b」，不写单个数（上下限一样时只写一个数）；最后一行写「按过去 34 天估算」，有准不准的数时接「，过去 2 周平均差 ±8%」，和自营业务的预计花费同一套说法。

邮件版（HTML）和文字版用同样的字、同样的顺序，只是排版不同；邮件多一张「近 14 天消费」柱状图：

- 顶上「炬元 · My Site 日报」，下一行「10月15日（周四） · 由炬元控制台生成」（「·」两边都空一格，和邮件里别处一样）。
- 消费、收入、毛利、净利四个格子。消费下面写「环比 +12.3% · 比前 7 天日均高 12.2%」；收入下面写「管理员自用 ¥234.00」（是 0 不写）；毛利下面写「毛利率 40.0% · 上游成本 ¥600.00」，净利下面写「净利率 30.0% · 固定成本 ¥100.00」。亏损的数字仍用墨色，利润率换成红色的「亏损」。读不到的格子写「没读到」：收入那格下面写收入的原因；毛利、净利两格下面照常写上游成本、固定成本，成本也没读到时写「上游成本 没读到（原因）」「固定成本 没读到（原因）」——和文字版说的是同一件事。
- 「利润怎么算」紧接在四个格子下面（和文字版一样在经营概览里），再下面是「近 14 天消费」柱状图：左下写第一天「10月2日」，右下写「10月15日 · ¥1,234.00」。
- 管理员的标记用次要颜色，不标红；「利润怎么算」用墨色，不标红。「（这天没有消费）」「（还没有上游）」「（用户身份没读到，管理员没标出）」和文字版一样带括号。
- 上游余额右边写余额，下面一行写「约 ¥28.80」或「没设置汇率」。档位名的颜色和上游列表一样：红色是余额用完、读不到余额和提醒天数以内的，黄色是余额偏低和 7 天以内的；不再续费的不标颜色。
- 页脚「由炬元控制台生成 · 每日经营日报」。

收入或成本没读到时日报照发：定时发送先按退避重试，最后一次还没读到才发这份；「立即发送」直接发这份。

**日报里每日利润只写一行（新）**，条数和页面「需处理」区块的条数来自同一份列表：

- 有要处理的：「每日利润：有 3 条需处理」，下一行「去处理：链接」，链接打开「每日利润」页（新：地址带 `#attention`，滚到「需处理」区块）。
- 放在哪（新）：文字版写在「■ 经营概览」最后、「利润怎么算」下面；邮件版在「利润怎么算」下面一个浅底条，「去处理」是链接（画成按钮的样子）。
- 没有要处理的：「每日利润：没有需处理的」，不带链接。
- 没配置控制台地址时，「去处理：」后面写「打开炬元控制台的「每日利润」页」。
- 读不到时：「每日利润：没读到（原因）」，原因按 §8 归类。
